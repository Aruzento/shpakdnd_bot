# V1.4.2: ручной запуск и протокол стенда

Запуск выполняет пользователь. Codex не подключается по SSH, не запрашивает
пароль и не запускает стенд/production. Все действия ниже относятся только к
подтверждённому тестовому серверу VM-338333 (`88.214.54.194:22`). Похожие пути
есть и на production: перед действиями проверить именно сервер и тестовый бот.

| Назначение | Подтверждённое значение |
|---|---|
| Конфигурация отдельного Telegram-бота | `/opt/shpakdnd-bot/.env` |
| Настройки чатов/тем | `/opt/shpakdnd-bot/app/topics.py` |
| Отдельная тестовая SQLite | `/opt/shpakdnd-bot/shpakdnd.db` |
| Внешняя сохранённая конфигурация тем | `/etc/shpakdnd-staging/topics.py` |
| Systemd unit | `/etc/systemd/system/shpakdnd-bot.service` |
| Mini TEST | `-1003883723333:2` |
| Обычный D&D TEST, чат без тем | `-5320347021:0` |

Токен не выводить в терминал/лог/чат. `.env` не копировать в отчёт или offline
checkout. Не использовать `sudo deploy-shpakdnd`: текущая команда нацелена на
`origin/main`, а V1.4.2 не объединена с main.

## 1. Долгие проверки до остановки тестового бота

В отдельном shell-сеансе на VM-338333:

```bash
set -euo pipefail
hostname
systemctl show shpakdnd-bot.service -p User -p WorkingDirectory -p ExecStart
cd /opt/shpakdnd-bot
git status --short
git rev-parse HEAD
git fetch origin
TARGET_SHA='<полный итоговый SHA из отчёта Codex>'
test "$(git rev-parse origin/codex/v1.4.2)" = "$TARGET_SHA"
# Создать новый каталог; если он уже существует, выбрать другой путь.
test ! -e /opt/shpakdnd-v142-check
git clone --no-hardlinks /opt/shpakdnd-bot /opt/shpakdnd-v142-check
cd /opt/shpakdnd-v142-check
git switch --detach "$TARGET_SHA"
test "$(git rev-parse HEAD)" = "$TARGET_SHA"
test ! -e .env
test ! -e shpakdnd.db
cp /etc/shpakdnd-staging/topics.py app/topics.py
export BOT_TOKEN='123456:offline-staging-check'
export PYTHONIOENCODING=utf-8
PY=/opt/shpakdnd-bot/.venv/bin/python
"$PY" - <<'PY'
from app.topics import TOPIC_SETTINGS
mini={(chat,thread) for chat,topics in TOPIC_SETTINGS.items() for thread,cfg in topics.items() if cfg.get('mini')}
assert mini=={(-1003883723333,2)}, mini
assert not TOPIC_SETTINGS[-5320347021][0].get('mini')
print('OK: isolated staging topics')
PY
"$PY" -m unittest discover -s tests -q > unittest.log 2>&1
"$PY" check_bot.py > check-bot.log 2>&1
"$PY" -m compileall -q bot.py app
"$PY" -m app.mini.combat.hero_abilities.validate
"$PY" -m app.mini.boss.boss_abilities.validate
"$PY" -m app.mini.tower.validate
"$PY" -m app.mini.validate_v142 > catalogs.json
git diff --check
"$PY" deploy/verify-v142-migration.py --source /opt/shpakdnd-bot/shpakdnd.db > migration-copy.json
```

Доказательство миграции выполняется на временной копии read-only источника.
`check_bot.py` выше создаёт БД **отдельного checkout**, не изменяет рабочую
тестовую SQLite. Проверить логи/exit codes. На Linux POSIX-тест должен выполниться;
нельзя механически переносить Windows-пропуск. Файл topics.py намеренно отличается
от релизного; остальные изменения исходников в checkout недопустимы.

## 2. Backup и установка SHA на тестовом стенде

Продолжать после успешной секции 1. В новом shell без фиктивного `BOT_TOKEN`:

```bash
set -euo pipefail
cd /opt/shpakdnd-bot
TARGET_SHA='<тот же полный SHA>'
OLD_SHA=$(git rev-parse HEAD)
git status --short
```

Если есть локальные изменения кроме app/topics.py, сначала отдельно сохранить
и разобрать их; не выполнять reset/clean/перезапись. Убедиться, что .env и
SQLite не tracked ни в старом, ни в целевом commit (`git ls-tree -r --name-only
"$TARGET_SHA" -- .env shpakdnd.db`). Для штатного локального topics.py сохранить
копию/patch вне checkout; внешний `/etc/shpakdnd-staging/topics.py` должен быть
актуален. Подготовить пользователя службы из `systemctl show`, права на БД и
каталог backup. Сохранить OLD_SHA и текущий status units в протоколе.

Если на стенде установлены и активны watcher/update units, остановить их перед
изменениями исходников; затем остановить `shpakdnd-bot.service` и проверить,
что polling-процесс и все writers завершились. Далее:

```bash
systemctl stop shpakdnd-bot.service
test "$(systemctl is-active shpakdnd-bot.service || true)" = inactive
BACKUP_DIR=/var/backups/shpakdnd-staging
mkdir -p "$BACKUP_DIR"
BACKUP="$BACKUP_DIR/v142-before-$(date -u +%Y%m%dT%H%M%SZ).db"
.venv/bin/python /opt/shpakdnd-v142-check/deploy/sqlite-deploy.py backup \
  --db /opt/shpakdnd-bot/shpakdnd.db --destination "$BACKUP"
.venv/bin/python /opt/shpakdnd-v142-check/deploy/sqlite-deploy.py check --db "$BACKUP"
printf 'Old SHA: %s\nTarget SHA: %s\nBackup: %s\n' "$OLD_SHA" "$TARGET_SHA" "$BACKUP"
# Stash только конфигурации тем сохраняет существующие локальные изменения.
git stash push -m 'staging topics before V1.4.2' -- app/topics.py
git switch --no-overwrite-ignore --detach "$TARGET_SHA"
test "$(git rev-parse HEAD)" = "$TARGET_SHA"
cp /etc/shpakdnd-staging/topics.py app/topics.py
```

Не удалять stash: это дополнительная восстановимая копия. `.env`, `.venv` и
SQLite остаются отдельными ignored файлами. После checkout проверить пути и
настройки scope, повторить assert из секции 1 и убедиться в отсутствии Mini
production-тем. Проверка config выполняется без вывода токена:

```bash
.venv/bin/python deploy/sqlite-deploy.py config \
  --db /opt/shpakdnd-bot/shpakdnd.db --project /opt/shpakdnd-bot
```

`check_bot.py` ниже применяет миграции уже к **тестовой** БД: выполнять от
пользователя службы, чтобы сохранить владельца файлов. Например, если User=shpakbot:

```bash
runuser -u shpakbot -- .venv/bin/python check_bot.py
runuser -u shpakbot -- .venv/bin/python deploy/sqlite-deploy.py check \
  --db /opt/shpakdnd-bot/shpakdnd.db
systemctl start shpakdnd-bot.service
systemctl is-active shpakdnd-bot.service
systemctl show shpakdnd-bot.service -p MainPID -p NRestarts
journalctl -u shpakdnd-bot.service --since '5 minutes ago' --no-pager
```

Если User другой, подставить фактическое значение. Проверить стабильный PID и
NRestarts через 10–30 секунд. Watcher возвращать только если он был активен и
его настройки проверены для стенда. Этот запуск не является production-релизом.

## 4. Восстановление тестового стенда

При неудаче сохранить журнал и текущую БД отдельно, остановить polling/writers.
Вернуть OLD_SHA и pre-migration backup согласованной парой, сохранить внешний
topics и .env. SQLite restore выполнять при остановленном боте, с корректными
владельцем/правами; наличие WAL/SHM требует закрытия всех соединений и аккуратного
восстановления через SQLite API, а не замены открытого файла. Проверить integrity/FK
и config перед запуском. Учесть потерю тестовых операций после backup. Эти
действия выполняет пользователь; production rollback отдельно не разрешён.
