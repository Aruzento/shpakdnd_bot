## Фактическая архитектура

bot.py -> app.handlers.ROUTERS -> обычные D&D handlers и Mini parent/subrouters.
Mini UI использует shared ui/context и transport; Events не импортирует private
handler API. Feature services владеют BEGIN IMMEDIATE и используют wallet API.
SQLite row/dict остаётся основным контрактом. connect_mini_db гарантирует close
и rollback. Coin/ledger SQL принадлежит wallet; shards имеют отдельную модель.

Boss combat.py — транзакционные use cases; calculations — hit math;
runtime — lifecycle; repository — snapshots/journal; rewards — выплаты;
boss_abilities — отдельные pure-ish hooks. Общие tags/matchups и hero_abilities
уже находятся вне Boss. Единственный активный выбранный герой snapshot-ится
при старте, выбор блокируется во fighting. Callback turn-token, write lock,
reward_granted и wallet operation_key защищают повторные действия.
Watcher восстанавливает persistent очередь/таймауты и публичные сообщения;
обычные timers восстанавливаются из своей БД.

Обработчики/DB обычного D&D, root/deploy, tests, content loaders, item registry,
конфигурация и router registration изучены. Новый статический проход по 95
модулям app не нашёл циклов явных абсолютных импортов; это не доказательство
отсутствия любых возможных runtime/dynamic cycles. Pure creature module отдельно
проверен в новом процессе: не импортирует Boss, config, SQLite или aiogram.

## Critical

Подтверждённых критичных дефектов baseline не найдено.

Риск расширения: включить бывшие metadata features посреди сохранённого боя,
повторно восстановить HP или смешать temporary HP с выплатой.
Где: boss/schema, combat, runtime, rewards.
Почему: поменяет состояние уже начатого боя и может повторно начислить награду.
Решение выполнено: additive defaults v0, new events v1; отдельное feature state;
одна SQLite-транзакция с журналом, общей процедурой смерти и прежней выплатой.
Сохранённые события до обновления (включая announced/ready) остаются v0.

## Future

1. Tower использует shared creatures/matchups/hero engine, со своей очередью,
   reward policy и persistent state; не копирует multiplayer Boss runtime.
2. Shard операции остаются transaction-aware SQL в разных service местах;
   общий helper нужен при росте use cases, без изменения coin ledger.
3. Обычный timer хранит один task на chat_id: отдельное продуктовое решение
   потребуется для независимых topic timers. Текущая семантика не менялась.
4. Контент/safety validation при startup и bounded caching каталогов:
   отдельный релиз с проверкой invalid-content startup behaviour.
5. Полноценные DB effect plan types и lifecycle notices из persisted journal:
   следующий шаг после стабилизации механик.

## Проверки и compatibility

Все семь feature/trait keys имеют shared vocabulary, Russian labels и описания.
demon трактуется как legacy alias demonic; нейтральная faction и ranger/magical
class остаются совместимыми. Один special_trait на героя подтверждён пользователем:
melee flying попадает, holy против flying требует ranged.

Ни один старый тест не удалён. Изменены только новые product contracts
(голем armor 3 -> 2, порядок description/passive, template mechanism -> none,
missing JSON defaults) и synthetic fixtures для прежних isolated passive tests.
JSON героя, цены, базовая атака/HP, faction assignments, rewards и economy
не менялись; единственная live-content migration — main ability iron_juggernaut.
Существующие SQL события/бой/кошелёк не мигрируют значения контента.

Реальная SQLite backup копия: все 23 таблицы и прежние колонки неизменны после
трёх init_mini_db/init_boss_db; integrity_check и foreign_key_check — OK.
Исходная shpakdnd.db сохранила SHA-256. Новые колонки принадлежат только
mini_bosses, а не участникам. Fresh/old/repeated schema, rollback, snapshots,
resurrection, callbacks, timeouts и выплаты проверяются integration tests.
