# D&D Mini V1.3 — реализация и проверка

Работа выполнена от HEAD `a9536f7` (новее контрольной точки
`5c44714f731391d0dc5c24cbf4c5451b8706d4bb`). Более новые изменения сохранены.
Исходное дерево было чистым. Push и polling не выполнялись.

## Реализовано

- 🏰 Испытания: 200 явных валидируемых floor records, один противник на этаж,
  видимые до выбора героя свойства, выбор из своей гачи, три щита, retry другим героем,
  first-clear progression, завершение после 200-го этажа и восстановление после restart.
- 🛡 Equipment: ровно 300 уникальных предметов с забавными fantasy-названиями;
  100 шлемов, 100 колец, 100 плащей, бонусы 1..100 в каждом слоте.
  Владение отдельно от equipped state; replace сохраняет старый предмет, unequip
  не удаляет владение. Максимум +300 ATK. Удаление последней копии очищает слот атомарно.
- `/superlook`, `/superadd`, `/superdel`, `/superchars`, `/superluck`: отдельный
  feature со strict parser, numeric access, transaction-aware service и persistent audit.
- Подключён `/create`, добавлен `/adminv`, `/admdel ... ALL` без учёта регистра.
  `/inv @user` и `/inv all` сохранены. `/add`, `/del`, `/clean`, `/admclean`
  удалены из handlers, текущей help и command configuration.
- `/admadd` обслуживает только ordinary D&D; Mini-перегрузка удалена.
  Общие timer/roll/start/chatid команды сохранены.
- Новые features подключены к существующим shared personal/ephemeral UI и startup.

## Границы модулей и транзакций

| Ответственность | Модули |
|---|---|
| Tower content / validation | `app/mini/tower/floors.json`, `catalog.py`, `validate.py` |
| Tower balance | `app/mini/tower/balance.json`, `balance.py` |
| Tower combat | `app/mini/tower/combat.py` |
| Tower use cases / persistence | `app/mini/tower/service.py`, `repository.py` |
| Tower UI | `app/mini/tower/handlers.py` |
| Equipment catalog | `app/mini/equipment/items.json`, `catalog.py` |
| Equipment ownership, equipped state, aggregate | `app/mini/equipment/service.py` |
| Equipment UI | `app/mini/equipment/handlers.py` |
| Mini superadmin | `app/mini/superadmin/access.py`, `parser.py`, `service.py`, `handlers.py` |
| Ordinary D&D vs Mini | `app/topic_guard.py` |
| Transaction-aware shared shards | `app/mini/shards.py` |

Tower не импортирует Boss combat, repository или compatibility aliases.
Canonical shared tags, integer matchups, hero hooks и creature hooks используются
через `app/mini/combat/`. Equipment не проходит через usable-item ItemEffectContext.
Coin balance и ledger меняются через existing wallet API.

Изменение attempt, first-clear claim, shards, предмет и progress фиксируются одной
`BEGIN IMMEDIATE` транзакцией. Unique `(player_id,floor)` claim и проверка
`attempt_id + expected_turn` исключают повтор награды и двойной ход. Partial unique
index разрешает один active attempt на игрока. Исключение откатывает всю операцию.
Mutating superadmin action и audit используют ту же транзакцию и стабильный key
`super:chat_id:message_id`; повтор сообщения не меняет ресурсы повторно.

## Миграция и persistent state

Добавлен ordered idempotent step `app/mini/migrations/v1_3.py` после historical
core/inventory/activities/legacy. Он выполняется в существующей Mini migration
транзакции и добавляет восемь таблиц:

1. `mini_equipment` — каталог.
2. `mini_equipment_owned` — владение и количество.
3. `mini_equipment_slots` — equipped code на слот игрока.
4. `mini_tower_progress` — highest cleared 0..200.
5. `mini_tower_attempts` — immutable hero/enemy snapshot, equipment bonus,
   HP, shields 0..3, callback turn, status, runtime и combat events.
6. `mini_tower_rewards` — уникальная first-clear запись, shards и equipment code.
7. `mini_gacha_guarantees` — персональный one-shot Legendary flag.
8. `mini_superadmin_audit` — actor/action/world/target/resource/code/amount/time/key.

Tower runtime сохраняет hit count, pending echo, защитные заряды, enemy skip,
creature state, число ответных actions и banked passive shards. Read paths не
запускают schema init или catalog sync. Каталоги валидируются и синхронизируются
на startup / explicit init. Старые таблицы не пересоздаются; stars, coins, shards,
Boss snapshots, migration history и legacy `demon -> demonic` сохранены.

## Атака и shared combat

`attack_before_matchups = current_hero_attack + equipment_attack_bonus`.

Звёзды используют существующее последовательное integer округление +50%.
Затем идут shared passive attack effects, faction multiplier (×2 / ×0.25 / ×1),
досягаемость и creature damage modifiers. Бонус экипировки фиксируется при старте
попытки; смена предмета или upgrade во время боя влияет на следующую попытку.
Equipment не внедрён в Boss balance.

Работают skip enemy attack, reward-guard как защита щита, echo, frenzy extra hit,
броня, полёт, resurrection, construct/holy regeneration и их technical/demonic
контрпики; hero poison/holy miss/construct recovery используют shared hooks.
Armored/undead starting reward buffers адаптированы в один guard charge при
сохранении строго 3/3 shields. Echo и extra hits не запускают обычные passives
повторно; kill hook действует только на обычный смертельный удар.

Часть магических/технических противников имеет явно заданный `response=prepare`:
первый ответный action готовит атаку, последующие бьют по щиту. Это видно до выбора
героя и даёт echo/frenzy шанс проявиться на четвёртом ходу. Другие противники
используют `response=attack`. При нуле щитов попытка проиграна до poison tick.

Boss-specific reward decay/corruption не переносится в Tower; rune_spark не
снимает несуществующий Tower magic shield. Demonic enemy взаимодействует со holy
hero; его Boss reward corruption не применяется. У shared engine и Boss режима
поведение не менялось. Combat shard procs копятся в попытке и выплачиваются
только вместе с first clear; проигрыш/retry не создают shards.

## Баланс и награды

Проанализированы actual catalog attacks:
Common 1..5, Uncommon 7..13, Rare 32..42, Legendary 150.
С существующими максимальными звёздами: Common 1..22 (4★), Uncommon 49..94 (5★),
Rare 364..474 (6★). Legendary: 225 / 337 / 505 / 757 / 1135 на первых пяти звёздах;
его звёзды остаются без ограничения, как в текущей игре.

Static HP records используют кривую `5 + floor + floor(0.07 * floor²)`:
6 HP на первом, 230 на 50-м, 805 на 100-м, 1730 на 150-м, 3005 на 200-м.
Слабый matchup уменьшает и Equipment, и звёздную атаку, а flying/recovery/armor
требуют подходящих свойств. Тест баланса подтверждает: на 140-м этаже Legendary
в плохом matchup проигрывает, тогда как развитый Rare-контрпик с тем же Equipment
побеждает. HP и диапазоны находятся в content/balance, вне handlers.

| Этажи | Shards за первый clear | Диапазон Equipment bonus сундука |
|---|---:|---:|
| 1–25 | 2 | +1…12 |
| 26–50 | 3 | +8…25 |
| 51–75 | 4 | +20…37 |
| 76–100 | 5 | +30…50 |
| 101–125 | 6 | +42…62 |
| 126–150 | 7 | +55…75 |
| 151–175 | 8 | +68…87 |
| 176–200 | 9 | +80…100 |

Базовая сумма — 1100 shards за всю Tower, без небольших shared passive procs.
Для сравнения: 4★ Common стоят 100 shards, 6★ Rare — 840, первые 4★ Legendary —
1000. Награда развивает коллекцию постепенно. Tower не начисляет coins.

Каждый пятый этаж автоматически открывает сундук: всего 40. Все слоты входят
в pool текущего диапазона; unseen предметы имеют приоритет. Если весь доступный
pool уже получен, выдаётся ещё один экземпляр валидного предмета. Дубликаты
не конвертируются в shards. Early pool не содержит +100.

## Superadmin и Mini/D&D

Единственный `SUPERADMIN_USER_ID = 694384548`, явно подтверждённый владельцем.
Авторизация только по `message.from_user.id`; username не участвует.
Нет назначаемой роли, allowlist, role-transfer UI или команд передачи.

Scope строго `chatid:themeid`, target — @username или numeric Telegram ID.
Ambiguous username требует numeric ID. Superlook без flags показывает всё;
с несколькими flags — выбранные ресурсы. Mutation принимает ровно один flag.
Coins/shards не могут стать отрицательными. Hero grant не создаёт duplicate shards;
hero deletion сохраняет корректный active selection и отклоняет используемого
в активной Tower/Boss героя. Item operations разрешают только существующие codes.

`superluck` хранит одну гарантию, не меняя global rarity weights. Следующий
успешный coin/ticket pull выбирает active Legendary, проходит обычное new/duplicate
resolution и снимает flag в pull transaction. Меню, недостаток денег, ошибка
платежа/commit и restart flag не расходуют. Повтор гарантии не складывает её.
Экран гачи показывает персональные 100%.

Shared topic guard проверяет current topic у `/create`, `/inv`, `/char`, `/charset`,
`/lvlup`; remote D&D admin handlers проверяют явный target topic до доступа к данным.
Все `/super*` проверяют target Mini world и enabled state. Ordinary D&D topic
super-командами не обслуживается.

## Практические ограничения и безопасные решения

Live Telegram polling / production deploy не запускались: проверены локальные
use cases, UI contracts и startup checks. Watcher path unit включает новые
директории; при deploy требуется переустановка path unit по existing инструкции.

Неограниченные звёзды Legendary сохраняются для совместимости. Поэтому достаточно
сильно прокачанный подходящий Legendary может превосходить часть контрпиков;
Tower не вводит скрытый nerf/cap для уже существующей коллекции. Flying и слабые
matchups остаются ограничителями. Rune_spark и Boss-only reward effects сохраняют
свой применимый к Boss scope; UI Tower отображает применимые enemy механики.
