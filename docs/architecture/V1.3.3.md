## Persistent Tower hero

Новая additive migration `app/mini/migrations/v1_3_3.py` подключена к обычной
упорядоченной идемпотентной цепочке `init_mini_db`. Таблица
`mini_tower_selections(player_id PRIMARY KEY, hero_id)` содержит один выбор
для scoped Mini player. Player уже принадлежит world, поэтому один Telegram
аккаунт в двух worlds имеет независимые selections. FK на player, hero и
составное владение `(player_id, hero_id)` используют ON DELETE CASCADE.
Floor и attempt в таблице отсутствуют; миграция не меняет старые snapshots.

`tower.repository.selected_hero` возвращает только существующего owned active
героя; недоступная запись безопасно удаляется. Catalog startup уже отключает
героев, отсутствующих в актуальном JSON. Conditional cleanup не удаляет
конкурентно сохранённый валидный выбор. Stars и ATK читаются заново для следующей
попытки. Новый контент/individual passive_key не добавляется.

`tower.service.select_hero` сохраняет выбор атомарно под BEGIN IMMEDIATE.
Пользовательский callback передаёт expected_floor; устаревший этаж и активная
попытка запрещают изменение через UI. `get_state` возвращает selected_hero.
Без выбора открывается общий selector V1.3.2: Favorites, All, Filters.
После выбора показываются текущий герой, «⚔️ Начать бой», «🔄 Сменить героя».
После победы следующий этаж использует этот же выбор; после поражения его
также можно повторить. Изменить выбор можно между боями через тот же selector.

`start_selected_attempt` под одним write lock проверяет актуальный этаж,
отсутствие active attempt, selection и ожидаемый hero_id. Это защищает старую
кнопку Start после смены выбора. Затем используется прежний create_attempt:
hero_json, enemy_json, equipment_bonus и runtime_json фиксируются как раньше.
Запущенный бой читает свой snapshot; изменения selection, stars, global active
или каталога не переписывают его. Legacy `start_attempt` остаётся совместимым
внутренним API; пользовательский flow всегда использует проверенный selection.
Ownership, personal/world context, пагинация, filters и ephemeral transport
остаются в существующих feature boundaries.

## Global active ✅

`ui.hero_selector.hero_label(..., active_marker=False)` по умолчанию не добавляет
галочку. Только renderer режима Collection (`mode == 'c'`) включает этот флаг:
Favorites, Show All и Results. `get_player_heroes` каждый раз получает is_active
из текущего mini_players.active_hero_id; marker не кэшируется. Галочка переносится
при следующем render после `set_active_hero`. Favorite membership и порядок
не меняются. Boss/Tower selector и строка текущего Tower hero галочки не получают.
Global active hero и persistent Tower selected hero — разные состояния.

## Production deployment

Основной script: `deploy/deploy-shpakdnd.sh`. Одноразовая установка:

```bash
cd /opt/shpakdnd-bot
sudo bash deploy/install-deploy-shpakdnd.sh
sudo deploy-shpakdnd --dry-run
# каждый обычный релиз:
sudo deploy-shpakdnd
```

Installer сохраняет root-owned bundle вне checkout и symlink команды; rollback
на предыдущий Git HEAD не удаляет command/tooling. Helpers фиксируются во
временной копии на время deploy. Existing filesystem watcher/update script
и units не менялись. Полная инструкция: [deployment.md](../deployment.md).

Flow: flock → clean/config/unit checks → fetch при работающем боте → показ
old/target и подтверждение → maintenance notice → stop path/update oneshot/bot
→ SQLite backup → повторное подтверждение pinned SHA → безопасный checkout
main на target → startup/schema + validators + весь suite + DB/Git checks
→ подтверждение запуска → проверка bot active/PID/restarts/journal → watcher
active и повторная health check → завершение maintenance с коротким SHA.

Notice helper читает существующий app.config/.env и SQLite mini_worlds,
отправляет во все enabled chat/topic через stdlib Bot API, без зависимости от
running bot и без печати токена. Неудача первого notice требует отдельного
подтверждения; финальная ошибка — WARNING после здорового запуска.
Backup выполняется `sqlite3.Connection.backup`, эксклюзивный файл проходит
integrity/FK checks. Backup: `/opt/shpakdnd-backups`; deployment logs:
`/var/log/shpakdnd-deploy`, root mode600, redaction .env/Telegram tokens.

Pipeline под shpakbot: compileall, runtime DB_PATH, check_bot.py (существующий
startup/init migration path), hero/boss/Tower validators, полный unittest suite,
SQLite integrity/FK. Также release diff --check, HEAD и clean worktree.
Failed check сразу останавливает pipeline. Выбор: оставить stopped или
подтвердить code rollback на Old SHA. Rollback проходит проверки и health
checks перед запуском. DB backup автоматически не восстанавливается: additive
migration и данные после backup не должны исчезнуть. Неуспешный target deploy
возвращает non-zero даже после успешного recovery. Failed start показывает
status/journal, останавливает unhealthy стек и предлагает rollback; ending
notice запрещён. SIGINT/SIGTERM выводят states/HEAD/backup без скрытого запуска.
Dry run выполняет preflight/fetch, без notice/stop/checkout/mutation/tests.

## Ограничения

Реальный production deployment/Telegram sends не выполнялись. На Windows
использован Git Bash с fake systemd/Git/Telegram и временными paths; реальные
Linux permissions/flock/systemd нужно подтвердить серверным dry run и первым
контролируемым deployment. Это не заменяет health проверки production.
Deployment не устанавливает dependencies и не восстанавливает DB автоматически.
Persistent selection применится к следующим attempts, старые активные бои
сохраняют snapshots. Каталоги героев/этажей/предметов, combat/balance и
существующий watcher остаются без изменений.
