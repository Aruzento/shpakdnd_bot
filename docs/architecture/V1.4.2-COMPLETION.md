Архитектура сохранена: handlers → services → transaction-aware SQLite/pure engines.
Канонический wallet и существующий shared combat не заменены. `home.py` содержит
маленькие чистые builders, чтобы registration не зависел от приватного handler.
Нет нового ORM/DI/event bus или исполняемого JSON-движка. Глобальные locks/cache,
которые существовали для Telegram транспорта, не являются источником нового игрового
состояния: batch, registration, retry и публикации восстанавливаются из SQLite.

## Решения по девяти конфликтам §2

1. **Жильцы:** из Домов сохранён вход «Жильцы»; четыре на страницу / 2×2;
   карточка «Снять с производства», «Выселить», «Назад» к той же странице.
2. **Работники:** добавлять можно только поселенца без работы. Перевод — снять,
   затем добавить в другую работу. Никаких скрытых transfers; производство не менялось.
3. **Mythic:** вход из «Ещё», обратный переход туда же. Не удалена existing crafting logic.
4. **Регистрация:** единый create screen; новая private цепочка и прежняя `/minicreate`.
   Legacy `created` безопасно ведёт домой. Starter gift ровно один раз. Private имя
   не публикуется; старый командный public welcome не изменён.
5. **Купоны:** выбор из реальных трёх quantity в inventory, отдельное подтверждение,
   существующий `useconfirm` service и стандартная карточка. Pity/luck/admin не меняются.
6. **×10:** цена 10 × текущая single price, только coins, без скидки/билетов;
   десять последовательных прежних круток внутри одной транзакции.
7. **Башня:** новая 3-stage цепочка; старые selector callbacks/render API совместимы;
   Boss selector не переделан. В активной попытке выбирать героя нельзя. Retry — реальный service.
8. **Шарды:** существующий доступ «Продать осколки» сохранён в карточке при наличии;
   курс 1:1 и экономика не менялись.
9. **Возвраты:** гача → гача, карточка → исходный список/фильтр/страница, житель →
   residents/page, Mythic → more, equipment из Tower → Tower. Events/пустые списки имеют выход.

## Сервисы, идемпотентность и временное состояние

- `gacha.perform_gacha_batch`: frozen цена, полный debit через wallet,
  десять `_perform_pull_in_transaction` с прежними RNG/weights/pity/luck/admin.
  Сохранены 10 `mini_gacha_pulls` и связи с позициями; batch/result/hero snapshots
  неизменны при новом каталоге/звёздах. Card actions используют текущий owned hero.
  Повтор owner/operation возвращает старый результат прежде проверки уже потраченных coins.
  «Ещё 10» создаёт новый nonce. Недостаток ресурса/пула, fault на шестой крутке
  и аварийный exit процесса откатывают весь платёж/pity/luck/героев/шарды/history.
- `registration.py`: owner-bound запросы 30 min, pending/activate/cancel/complete;
  создание персонажа и существующие 3 starter tickets в одной транзакции.
  TTL/wrong owner/disabled world/control/hidden Unicode/HTML/commands отвергаются.
  Старый запрос после другой завершённой регистрации не перехватывает private текст.
- `ui/state.py`: durable owner context и single-publication reservation.
  Legacy operation keys основаны на chat/topic/сообщении/действии, не новом query ID.
  Участники не могут открыть чужие batch/context или менять чужое состояние.
- `tower.retry_attempt`: одна новая попытка на source lost attempt, общий existing
  transaction/start pipeline; повтор возвращает её после рестарта. На сохранении
  проверены owner, актуальный этаж, наличие героя, village/other-battle/active guards.
- Village: revision и return-screen validation до мутации; settlement/job/eviction
  не удаляют owned hero и уже заработанные ресурсы; replay не начисляет дважды.
- Telegram failure после commit batch не списывает повторно; результат доступен
  повтором той же кнопки. Перед публичной share запись claim предотвращает duplicate.
  При неопределённом результате отправки нет автоматического resend: это может
  оставить непоказанную публикацию и требует осознанного нового действия пользователя.
- Shared context/transport допускает проверенную private навигацию после имени,
  сохраняет ephemeral в Mini-теме; private callback не отправляет personal экран в группу.
  Ссылки/публичные анонсы сохраняют прежний intentional public flow.

## SQLite и rollback evidence

Новая миграция `app/mini/migrations/v1_4_2_ui.py` подключена к прежнему orchestrator;
DDL выполняется внутри его BEGIN IMMEDIATE, повторно запускается и не меняет старых колонок.

| Новая таблица | Контракт |
|---|---|
| mini_gacha_batches | unique(player,operation), fixed price/total, immutable summary |
| mini_gacha_batch_pulls | unique batch/position 0..9 и pull, FK к 10 standard results |
| mini_registration_requests | owner/world/TTL/pending/completed player |
| mini_ui_navigation | opaque token, player, screen/context |
| mini_ui_publications | player/operation PK, durable pre-send reservation |
| mini_tower_retries | source lost attempt PK, owner, unique new attempt |

`deploy/verify-v142-migration.py --source <source.db>` открывает источник только
`mode=ro`, делает SQLite backup в temporary directory и трижды применяет миграции.
Проверка исходной пользовательской SQLite: **36 старых таблиц / 349 строк**,
старые columns/values сохранены, registry sync сохраняет user rows и item IDs,
`integrity_check=ok`, `foreign_key_check=0`. Production DB не мигрировалась.
Fresh DB, legacy schema и повторный запуск покрыты full suite; fixture seeds включают новые таблицы.

`deploy/verify-v142-rollback.py --source <source.db> --old-ref <40-char SHA>`:
копия + current check_bot + реальные новые batch/name/navigation/publication/retry
состояния, затем old-code startup из git archive. Проверены:

- PR baseline `293693d87692bb9e7f4567bcca895e799e7455d2`;
- main baseline `f06c0d129fdad0fef4fde0889915faac26b94f4a`.

У обеих check_bot exit=0, все user tables неизменны, definition IDs сохранены,
integrity ok/FK 0. Это **startup/data-preservation proof**, не доказательство того,
что старый UI понимает новые batch/retry. Предпочтительный code rollback — на PR baseline,
который уже содержит новые предметы/pity/Spirit/currencies/Shadow. Main содержит более
старый каталог (49 вместо 54 героев / 6 вместо 10 товаров) и может деактивировать
новые definitions: откат на него требует отдельного решения по code+catalog bundle.
Нельзя автоматически подменять актуальную DB старым backup после новых операций:
так теряются новые пользовательские действия. Откат здесь не выполнялся.

Добавлены **163 теста**: 20 core, 29 integration/navigation, 114 screen contracts

Final-SHA результаты и точный SHA передаются в PR/final report после повторного полного
запуска на коммите. Команды обязательного gate:

```bash
python -m unittest discover -s tests -v
```

они есть в baseline. Asyncio slow-task diagnostics при CPU/SQLite тестах не означают

лог-выводы содержат counts/hashes, без inventory/private names/token data.

## Release gate, стенд и восстановление

**Не выполнено:** независимое review, 47 сценариев реального Telegram-стенда,
Linux/systemd/watch unit runtime, postdeploy smoke, production backup/restore.
Из архива перенесены требования, а не разрешение исполнять production commands.
Перед передачей стенду необходимо:

1. Зафиксировать candidate SHA, `git show --stat`/diff, все final-SHA logs и matrix;
   отдельные BOT_TOKEN и SQLite для стенда, сохранённая копия каталога/изображений.
2. Пройти все 47 сценариев §13 ТЗ с логами: private registration и topic/owner,
   changed keyboards/images/back, ×10/coupon/replay/concurrency/restart, Village,
   Tower selection/retry/snapshots, Spirit/Shadow, D&D currency isolation, recovery.
3. На Linux проверить существующие `shpakdnd-bot.service.example`,
   `shpakdnd-bot-watch.path`, `shpakdnd-bot-update.service` и deploy scripts:
   один polling процесс, корректный Python/venv/path/env, watcher не перезапускает
   непрерывно, новые файлы покрыты directory watch. Не менять production unit для теста.
4. После review+стенда отдельно согласовать merge/deploy/backup/rollback. Длительные
   проверки выполнять до downtime. Остановить polling/watcher, SQLite backup API
   (включая WAL state), проверить integrity и безопасно сохранить `.env`/каталоги.
5. Postdeploy smoke после согласования: один bot process; startup/routers/catalogs;
   owned menu/name/collection, 1/10/coupon saved results, Boss восстановление активного
   хода, Tower immutable loadout/retry, Village accrual, D&D inventory/currency scope.
6. При сбое остановить bot/watcher, сохранить failed DB+logs; сначала предпочесть
   исправление/code rollback на проверенный PR baseline с новым каталогом. DB restore
   требует явного разрешения и оценки потери новых действий; проверить copy до запуска.

Риски для review/стенда: Telegram ephemeral/photo поведение невозможно доказать mocks;
sync writer при ×10 нужно измерить на нагрузке; callback taxonomy contexts нужно
инвалидировать при будущей смене enum/catalog filters; TTL housekeeping для UI rows;
publication claim при timeout исключает дубль ценой возможного пропуска публикации;
main rollback не знает новую семантику UI и использует устаревший каталог.
Открытых failed automated checks по текущей реализации нет; это не production-ready.
