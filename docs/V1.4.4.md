## Источники и runtime

Рабочие файлы находятся вне checkout/watcher, обычно /var/lib/shpakdnd:

- loot.csv: мастер, DND_LOOT_CSV_PATH.
- loot_code_map.csv: постоянный индекс code,name. Первичное loot_000001 допустимо;
  перестановка, удаление и возврат строк не меняют код. Удалённые коды зарезервированы.
- shop_offers.csv: ручной ассортимент chat_id,thread_id,code,buy_enabled,stock.
  В data/shop_offers.example.csv только заголовок, ни одного разрешённого товара.
- shop.csv: скомпилированный runtime, DND_SHOP_CSV_PATH; соседние
  shop.csv.lock и shop.csv.previous.

Смена пути требует отдельного планового restart; публикация содержимого — нет.
В Git хранятся эталонные входы, а не рабочие файлы. data/loot_code_map.csv —
индекс для новой чистой установки; **не копируйте его поверх существующей истории**.
Команда index сохраняет прежние SKU из БД, например short_sword.
Коллизии между темами и переименования требуют рассмотренной миграции.
Fuzzy/подстрочного поиска нет; чужой item_id и неоднозначные NULL не исправляются.

В runtime присутствуют все 4450 позиций для каждого явно выбранного обычного
scope с настроенным admin. Mini/неизвестные темы отклоняются.
Старые колонки chat_id,thread_id,code,name,description,price,stock,active
дополнены buy_enabled,rarity,category,effect,master_sha256.
Хеш связывает цены и справку с мастером. Пропущенная позиция, другая цена,
неполная схема, конфликт валюты в покупке, повтор имени/SKU блокируют кандидат.
После master-импорта legacy/пустой CSV запрещён. До первого импорта старая
8-колоночная схема совместима. Старое active=false сохраняется, включая tombstone после удаления позиции,
и автоматически не включается. Пределы: 32 MiB, 25000 runtime строк, поле 65536, имя 256 символов.
Два полных scope дают 8900 строк / примерно 11,3 MB. Превышение отклоняется
целиком; строки не усекаются. Слишком много тем требуют согласованной конфигурации.

Без ручного offer покупка выключена. Выкуп определяется членством в мастере,
не зависит от buy_enabled, stock и sold; системные валюты исключены.
active=false блокирует оба направления. stock — накопительный лимит:
доступно max(0,stock-sold); при sold=4 изменение stock 5→10 оставляет 6.
Выкуп не пополняет stock/sold. Выключение/возврат SKU не сбрасывают историю.

## Validate → publish

Работать от пользователя службы с тем же окружением. Родительский каталог
доступен ему на чтение/запись/поиск, CSV на чтение, lock на чтение/запись.
Рекомендуются закрытая группа, каталог 0750, файлы 0640; посторонним запись
запрещена. Проверить service User/Group и test -r/-w/-x под этим пользователем.
Первая публикация 0640, при замене сохраняется mode старого файла.
ACL/SELinux проверяются отдельно на сервере. Нужна локальная ФС с flock и atomic
rename, не SMB/NFS. Lock-файл нельзя удалять или заменять.

Ниже инструкция будущего согласованного TEST. SQLite — инициализированная
**изолированная копия**, не PROD. CLI не запускает polling.
Live источники, индекс, staging и runtime внутри checkout запрещены.

~~~bash
python -m app.dnd_shop.cli index \
  --loot /var/lib/shpakdnd/loot.csv --map /var/lib/shpakdnd/loot_code_map.csv \
  --scope=-5320347021:0 --db /PATH/TO/ISOLATED/TEST.db

python -m app.dnd_shop.cli build \
  --loot /var/lib/shpakdnd/loot.csv --map /var/lib/shpakdnd/loot_code_map.csv \
  --offers /var/lib/shpakdnd/shop_offers.csv --scope=-5320347021:0 \
  --output /var/lib/shpakdnd/shop.next.csv --db /PATH/TO/ISOLATED/TEST.db

python -m app.dnd_shop.cli validate /var/lib/shpakdnd/shop.next.csv \
  --loot /var/lib/shpakdnd/loot.csv --db /PATH/TO/ISOLATED/TEST.db
python -m app.dnd_shop.cli publish /var/lib/shpakdnd/shop.next.csv \
  --loot /var/lib/shpakdnd/loot.csv --db /PATH/TO/ISOLATED/TEST.db
python -m app.dnd_shop.cli audit --db /PATH/TO/ISOLATED/TEST.db
~~~

Повторяйте --scope для нескольких тем. При отсутствии offer сборщик сохраняет
прежний stock, но выключает покупку; inactive сохраняется. Для старой БД перед
validate нужна аддитивная миграция копии новым init_db. Index открывает БД
read-only. Build создаёт staging и проверяет весь мастер/связи в откатываемой
транзакции. Validate ничего не фиксирует. Отчёт: считано, импортировано, на тему,
выключено покупок, разрешено предложений, ошибки, SHA.

Publish фиксирует байты кандидата, fsync, получает exclusive отдельный lock,
повторяет validate, сохраняет прежние байты в .previous, os.replace, fsync
родителя. При ошибке старый runtime сохраняется. Мастер хранить версионно:
новый мастер, индекс, offers и кандидат готовятся согласованно; менять мастер
посреди публикации запрещено процедурой. При неудачной публикации вернуть
прежний мастер. Runtime нельзя вручную смешивать с другой версией источника.

Порядок блокировок: **catalog lock → SQLite BEGIN IMMEDIATE → COMMIT/ROLLBACK
→ unlock**. Торговля shared flock, publisher exclusive; Windows shared
эмулируется exclusive byte-range. Timeout 5 секунд, без скрытого повторения
транзакции. Прямое nano/cp гарантий publish не обеспечивает.

Иммутабельный snapshot проверяется открытием файла и fstat
(inode/size/mtime_ns/ctime_ns/mode) под lock на каждом callback. При изменении
файл перечитывается/хешируется. Ошибка чтения/парсинга не даёт старый кеш.
SQLite хранит digest по runtime пути; полный sync только на новом digest
в одной транзакции вместе с новыми item_id. Restart перечитывает snapshot,
но прежняя SQLite версия не пересинхронизируется. Сделка заново проверяет
предмет, валюты, владение, инвентарь и подтверждённую цену.

## Точный credit и атомарность

Номиналы прежней обычной D&D системы:
Fraction(Decimal(base_value))/currency_quantity; деньги только в inventory.
Ограниченный размен ищет точную оплату, затем минимальную переплату;
неограниченный минимизирует монеты сдачи. Большие выплаты используют доказуемый
алгоритм остатков по максимальному номиналу. Пределы: 200000 состояний,
2000000 шагов на план, 128 кандидатов coin+credit, 32 номинала.
Превышение — отдельная ошибка расчёта, не математическая невозможность.

Если точные 3% невозможно выдать монетами, **вся** выплата становится credit
на проверенном (chat_id,thread_id,user_id,username). Это обязательство торговца,
не предмет, не монета и не Mini wallet. Если размен возможен, выдаются монеты.
При покупке расходуется максимально допустимая точная часть credit, затем
монеты. Остаток 0,03 с целыми монетами может сохраниться при покупке за 1;
0,5 credit + 1 монета оплачивают 1,5 без округления.

Главное меню по-прежнему ровно Купить / Продать / Выйти. Остаток показан текстом;
обмен доступен из списка/квитанции, с отдельным подтверждением. Обменивается весь
остаток только при точном размене. Иначе он сохраняется. Изменившийся остаток
требует нового подтверждения.

Новые таблицы: dnd_shop_catalog_versions, dnd_shop_catalog_entries,
dnd_shop_credit, dnd_shop_credit_moves, dnd_shop_credit_redemptions,
dnd_shop_credit_coins. В operations добавлена nullable quote_digest.
Прежние 6 таблиц/их CHECK, item_id/NULL и пользовательские строки сохранены.
Суммы TEXT в каноническом Fraction: 3/100, 1, 0. Движения связаны с trade_id
или одноразовым redemption token, уникальность предотвращает двойное начисление.

Сделка проверяет Telegram ID+username+персонаж+scope+токен и меняет предмет,
монеты, credit, sold, журнал и квитанцию в одной BEGIN IMMEDIATE. Ошибка —
полный rollback. Повтор после COMMIT возвращает сохранённую квитанцию даже
после ошибки Telegram. Разные токены последней вещи не дают двойную выплату.
Смена цены/ассортимента/stock/master версии отменяет старую покупку;
новая цена продажи требует повторного действия. Audit проверяет SQLite/FK,
журнал, остатки, квитанции и равенство стоимости монет+credit цене.

## Проверки и независимое ревью

В Linux workflow сохранён весь набор из ТЗ и PTY проверки V1.4.3.1
для Python 3.11/3.13. tools/benchmark_dnd_shop.py использует реальный мастер
и два синтетических scope только во временной БД: 8900 импортов, один явно
тестовый offer. Измеряет cold/warm, SQL, память tracemalloc, buy/sell/restart,
проверяет аудит. CLI дополнительно проверяет tools/validate_dnd_loot_cli.py на настоящем master.
JSON артефакт CI: loot-benchmark-python-VERSION.
На warm цикле трёх экранов проверяются <100 SQL и 0 полных sync.
critical_wall_s включает ожидание lock: это верхняя оценка критической секции,
не сетевая Telegram задержка. Порог latency не подменяет фактические метрики.

tools/validate_dnd_shop_release.py проверяет V1.4.3, V1.4.3.1 и SHA96ff:
NULL/REAL/TEXT, прежние SKU/sold/квитанции/pending, три init_db, атомарный DDL
fault, integrity/FK и startup старого кода. --source /PATH/TO/FRESH/BACKUP.db
открывает источник read-only и делает SQLite online backup в disposable copy.
Данные и дампы не входят в Git. Если свежая production backup недоступна,
эта часть приёмки **не подтверждена**; синтетические проверки её не заменяют.

Два прежних теста обновлены по решению владельца: невозможная выдача 3% теперь
проверяет credit, исчерпанный stock скрывается. Квитанции одинаковы при первом
и повторном вызове (JSON списки). Тесты не удалены/не отключены.
Прежние Windows skip Linux PTY остаются; Linux обязан выполнять их все.
