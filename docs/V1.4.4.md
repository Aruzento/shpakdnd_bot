## Подлинный источник и единицы

В data/loot.csv сохранён оригинал без изменения байтов.
Отдельное разрешение владельца на публикацию в Git/CI получено.
SHA-256: 7bffd8a9b8314651318c961838c9b6b872f5d02b6cd896e968f9226c7bcdfe20.
Размер 5 188 747 байт, 4 450 записей, 16 категорий, 8 редкостей.
UTF-8; разделитель «;», шесть колонок:

~~~text
Предмет;Эффект;Описание;Стоимость;Редкость;Категория
~~~

Поля сохраняются полностью: максимум эффект/описание 13 176/13 159 символов.
Эффект — справка, боевых действий не выполняет. Telegram выводит выдержки,
parse_mode=None, в пределах UTF-16 лимита, не меняя источник.

Исходная цена целая 1..350000000. Режим -m сохраняет её в единицах реальной
базы темы: короткий меч стоит 35000. Режим -b умножает исходную цену точно
на 0.0285 универсальных медных или 0.000285 универсальных золотых.
100 универсальных медных = 1 универсальная золотая. Для исходных
1/100/3500/35000 получаем 0.0285/2.85/99.75/997.5 медных или
0.000285/0.0285/0.9975/9.975 золотых. Максимальная исходная цена 350000000
даёт 9975000 медных или 99750 золотых. Коэффициент не заменяется на 1/35.
Покупка 100%, выкуп одной штуки — ровно 3% выбранного режима. Fraction/Decimal,
без float/округления. Исторические квитанции не переоцениваются.
Валюты регистрируются существующими /admcoin и /admscoin до импорта.
Команда создания проверяет явный набор денежных единиц, а не слово «монета»:
кошель с монетами остаётся предметом. Обычная вещь на месте денежной единицы
требует отдельной рассмотренной миграции; автоматического превращения в деньги нет.

## Источники и runtime

Рабочие файлы находятся вне checkout/watcher, обычно /var/lib/shpakdnd:

- loot.csv: мастер, DND_LOOT_CSV_PATH.
- loot_code_map.csv: DND_SHOP_CODE_MAP_PATH, постоянный индекс code,name. Первичное loot_000001 допустимо;
  перестановка, удаление и возврат строк не меняют код. Удалённые коды зарезервированы.
- shop_offers.csv: DND_SHOP_OFFERS_PATH, ручной ассортимент chat_id,thread_id,code,buy_enabled,stock.
  В data/shop_offers.example.csv только заголовок, ни одного разрешённого товара.
- shop.csv: скомпилированный runtime, DND_SHOP_CSV_PATH; соседние
  shop.csv.lock и shop.csv.previous.

Смена пути требует отдельного планового restart; публикация содержимого — нет.
В Git хранятся эталонные входы, а не рабочие файлы. data/loot_code_map.csv —
индекс для новой чистой установки; **не копируйте его поверх существующей истории**.
Команда index сохраняет прежние SKU из БД, например short_sword.
Коллизии между темами и переименования требуют рассмотренной миграции.
Fuzzy/подстрочного поиска нет; чужой item_id и неоднозначные NULL не исправляются.

В runtime присутствуют все 4450 позиций для каждого явно выбранного обычного
scope с настроенным admin. Mini/неизвестные темы отклоняются.
Старые колонки chat_id,thread_id,code,name,description,price,stock,active
дополнены buy_enabled,rarity,category,effect,master_sha256.
Хеш связывает справку с мастером, цены проверяются по сохранённому фактору каждой темы. Пропущенная позиция, другая цена,
неполная схема, конфликт валюты в покупке, повтор имени/SKU блокируют кандидат.
После master-импорта legacy/пустой CSV запрещён. До первого импорта старая
8-колоночная схема совместима. Старое active=false сохраняется, включая tombstone после удаления позиции,
и автоматически не включается. Пределы: 32 MiB, 25000 runtime строк, поле 65536, имя 256 символов.
Два полных scope дают 8900 строк / примерно 11,3 MB. Превышение отклоняется
целиком; строки не усекаются. Слишком много тем требуют согласованной конфигурации.

Без ручного offer покупка выключена. Выкуп определяется членством в мастере,
не зависит от buy_enabled, stock и sold; системные валюты исключены.
Список продажи скрывает неизвестные/неактивные/неоднозначные/денежные позиции;
подтверждение заново проверяет соответствие на сервере.
active=false блокирует оба направления. stock — накопительный лимит:
доступно max(0,stock-sold); при sold=4 изменение stock 5→10 оставляет 6.
Выкуп не пополняет stock/sold. Выключение/возврат SKU не сбрасывают историю.

## Validate → publish

Работать от пользователя службы с тем же окружением. Родительский каталог
доступен ему на чтение/запись/поиск, CSV на чтение, lock на чтение/запись.
Рекомендуются закрытая группа, каталог 0750, файлы 0640; посторонним запись
запрещена. Проверить service User/Group и test -r/-w/-x под этим пользователем.
Первая публикация 0640, при замене сохраняется mode старого файла.
ACL/SELinux проверяются отдельно на сервере. Нужна локальная ФС с flock и atomic
rename, не SMB/NFS. Lock-файл нельзя удалять или заменять.

Ниже инструкция будущего согласованного TEST. SQLite — инициализированная
**изолированная копия**, не PROD. CLI не запускает polling.
Live источники, индекс, staging и runtime внутри checkout запрещены.

~~~bash
python -m app.dnd_shop.cli index \
  --loot /var/lib/shpakdnd/loot.csv --map /var/lib/shpakdnd/loot_code_map.csv \
  --scope=-5320347021:0 --db /PATH/TO/ISOLATED/TEST.db

python -m app.dnd_shop.cli build \
  --loot /var/lib/shpakdnd/loot.csv --map /var/lib/shpakdnd/loot_code_map.csv \
  --offers /var/lib/shpakdnd/shop_offers.csv --scope=-5320347021:0 \
  --output /var/lib/shpakdnd/shop.next.csv --db /PATH/TO/ISOLATED/TEST.db

python -m app.dnd_shop.cli validate /var/lib/shpakdnd/shop.next.csv \
  --loot /var/lib/shpakdnd/loot.csv --db /PATH/TO/ISOLATED/TEST.db
python -m app.dnd_shop.cli publish /var/lib/shpakdnd/shop.next.csv \
  --loot /var/lib/shpakdnd/loot.csv --db /PATH/TO/ISOLATED/TEST.db
python -m app.dnd_shop.cli audit --db /PATH/TO/ISOLATED/TEST.db
~~~

Повторяйте --scope для всех существующих тем общего runtime. Пропуск ранее
опубликованной темы отклоняется при validate/publish; её удаление требует отдельной миграции. При отсутствии offer сборщик сохраняет
прежний stock, но выключает покупку; inactive сохраняется. Для старой БД перед
validate нужна аддитивная миграция копии новым init_db. Index открывает БД
read-only. Build создаёт staging и проверяет весь мастер/связи в откатываемой
транзакции. Validate ничего не фиксирует. Отчёт: считано, импортировано, на тему,
выключено покупок, разрешено предложений, ошибки, SHA.

Publish фиксирует байты кандидата, fsync, получает exclusive отдельный lock,
повторяет validate, сохраняет прежние байты в .previous, os.replace, fsync
родителя. При ошибке старый runtime сохраняется. Мастер хранить версионно:
новый мастер, индекс, offers и кандидат готовятся согласованно; менять мастер
посреди публикации запрещено процедурой. При неудачной публикации вернуть
прежний мастер. Runtime нельзя вручную смешивать с другой версией источника.

Порядок блокировок: **catalog lock → SQLite BEGIN IMMEDIATE → COMMIT/ROLLBACK
→ unlock**. Торговля shared flock, publisher exclusive; Windows shared
эмулируется exclusive byte-range. Timeout 5 секунд, без скрытого повторения
транзакции. Прямое nano/cp гарантий publish не обеспечивает.

Иммутабельный snapshot проверяется открытием файла и fstat
(inode/size/mtime_ns/ctime_ns/mode) под lock на каждом callback. При изменении
файл перечитывается/хешируется. Ошибка чтения/парсинга не даёт старый кеш.
SQLite хранит digest по runtime пути; полный sync только на новом digest
в одной транзакции вместе с новыми item_id. Restart перечитывает snapshot,
но прежняя SQLite версия не пересинхронизируется. Сделка заново проверяет
предмет, валюты, владение, инвентарь и подтверждённую цену.

## Точный credit и атомарность

Номиналы прежней обычной D&D системы:
Fraction(Decimal(base_value))/currency_quantity; деньги только в inventory.
Ограниченный размен ищет точную оплату, затем минимальную переплату;
неограниченный минимизирует монеты сдачи. Большие выплаты используют доказуемый
алгоритм остатков по максимальному номиналу. Пределы: 200000 состояний,
2000000 шагов на план, 128 кандидатов coin+credit, 32 номинала.
Превышение — отдельная ошибка расчёта, не математическая невозможность.
Для проверенной продажи CalculationLimit выплаты также разрешает всю точную
сумму 3% в credit. Ошибки SQLite/валют/владельца/инвентаря/инвариантов
отменяют сделку без credit. При обмене CalculationLimit/невозможность размена
оставляет баланс неизменным. Ограничения ресурсов не увеличены.

Если точные 3% невозможно выдать монетами, **вся** выплата становится credit
на проверенном (chat_id,thread_id,user_id,username). Это обязательство торговца,
не предмет, не монета и не Mini wallet. Если размен возможен, выдаются монеты.
При покупке расходуется максимально допустимая точная часть credit, затем
монеты. Остаток 0,03 с целыми монетами может сохраниться при покупке за 1;
0,5 credit + 1 монета оплачивают 1,5 без округления.

Главное меню по-прежнему ровно Купить / Продать / Выйти. Остаток показан текстом;
обмен доступен из списка/квитанции, с отдельным подтверждением. Обменивается весь
остаток только при точном размене. Иначе он сохраняется. Изменившийся остаток
требует нового подтверждения.

Новые таблицы: dnd_shop_catalog_versions, dnd_shop_catalog_entries,
dnd_shop_credit, dnd_shop_credit_moves, dnd_shop_credit_redemptions,
dnd_shop_credit_coins. В operations добавлена nullable quote_digest.
Также добавлены dnd_shop_settings (scope, enabled, режим, точный фактор,
база, отпечаток валют, явные соответствия, версия настроек, timestamps;
CHECK формулы/полноты настроек и составной FK базы по теме) и
dnd_shop_publications (durable intent с хешем и bounded BLOB кандидата).
Прежние 12 таблиц/их CHECK, item_id/NULL и пользовательские строки сохранены.
Суммы TEXT в каноническом Fraction: 3/100, 1, 0. Движения связаны с trade_id
или одноразовым redemption token, уникальность предотвращает двойное начисление.

Сделка проверяет Telegram ID+username+персонаж+scope+токен и меняет предмет,
монеты, credit, sold, журнал и квитанцию в одной BEGIN IMMEDIATE. Ошибка —
полный rollback. Повтор после COMMIT возвращает сохранённую квитанцию даже
после ошибки Telegram, пока сессия действует и магазин не остановлен.
Остановка блокирует callback, но квитанции сохраняет. Разные токены последней вещи не дают двойную выплату.
Смена цены/ассортимента/stock/master версии отменяет старую покупку;
новая цена продажи требует повторного действия. Audit проверяет SQLite/FK,
журнал, остатки, квитанции и равенство стоимости монет+credit цене.

## Создание, отключение и валютная конфигурация

Только администратор текущей обычной темы из TOPIC_SETTINGS может выполнить
/shopcreate -b, /shopcreate -m, /stopshop. Используется существующая
check_topic_admin_permission и повторная проверка сервисом. Глобальный или
Telegram-администратор без назначения в теме не получает прав. Chat/thread
берутся только из сообщения; Mini/неизвестные темы отклоняются. Без одного
корректного флага — справка без изменений; сочетание флагов и ввод ID запрещены.

Нужна ровно одна активная база номиналом 1. После /admcoin и /admscoin задайте
в TOPIC_SETTINGS каждой темы явные соответствия стабильным dnd_items.code.
Узнать их read-only запросом SELECT id,code,name,category FROM dnd_items
WHERE chat_id=... AND thread_id=...; не копировать коды из другой темы.
Пример структуры (placeholders заменить реальными кодами):

~~~python
"shop_currency_units": {
    "master": {
        "Медная монета": "ACTUAL_REGISTERED_COPPER_CODE",
        "Серебряная монета": "ACTUAL_REGISTERED_SILVER_CODE",
        "Золотая монета": "ACTUAL_REGISTERED_GOLD_CODE",
    },
    "universal_copper": "ACTUAL_REGISTERED_UNIVERSAL_COPPER_CODE",
    "universal_gold": "ACTUAL_REGISTERED_UNIVERSAL_GOLD_CODE",
}
~~~

master обязателен для обоих режимов, это явный набор денежных единиц оригинала.
Для оригинала обязательны все 15 явно перечисленных денежных позиций:
Медная монета; 10/50 медных монет; Серебряная монета; 5/10/50 серебряных монет;
Золотая монета; 2/5/10/50/100/500/1000 золотых монет.
Пример выше показывает первые три записи: дополните master соответствиями
остальных 12 позиций, используя отдельные зарегистрированные currency item_id
для каждой связки. Номинал связки обязан равняться количеству × номиналу её
явно указанной одиночной монеты. Все 4435 остальных позиций остаются вещами
(кроме дополнительных явно зарегистрированных валют конкретной темы).
Кошельки, старинные и магические монеты автоматически валютами не становятся.
Дополнительные утверждённые денежные позиции мастера также указываются явно.
Каждый код принадлежит отдельной активной валюте этой темы, зарегистрированной
в dnd_currencies и dnd_items с category=currency. Имена могут отличаться:
монетные SKU связываются с существующими валютными item_id, как вещи не торгуются.
Одноимённая прежняя обычная вещь — отказ до импорта, без автоматической починки.
Для -b обязательны universal_copper/gold, gold=100*copper, база — одна из них.
Для -m универсальные соответствия не определяют цену; ответ сообщает реальную базу.
Команда не создаёт валюты, не меняет номиналы, не выдаёт вещи/монеты игрокам.

Подготовить вне checkout оригинальный loot.csv и постоянный индекс через CLI
index, затем /shopcreate в нужной настроенной теме. DND_SHOP_CODE_MAP_PATH и
DND_SHOP_OFFERS_PATH задают внешние пути; отсутствующий offers даёт пустую покупку.
Настройки источников/прав доступа описаны выше. Реальный TEST scope необходимо
явно настроить владельцу; демонстрационный scope не назначается автоматически.

Повтор с тем же режимом проверяет каталоги/валюты и включает остановленный магазин,
не сбрасывая sold, item_id, credit и журнал. Другой режим всегда отклоняется,
даже для пока пустого магазина: отдельного автоматического преобразования нет.
Прежняя история без нового состояния может быть принята только в -m.
База, формула, отпечаток активных номиналов и соответствия фиксируются в SQLite;
последующее изменение требует рассмотренной миграции, особенно при credit.

/stopshop сохраняет enabled=false и закрывает старые сессии в BEGIN IMMEDIATE.
Другие темы не затрагиваются. Старые кнопки не оживают после повторного включения.
История/credit/квитанции сохраняются. После restart /shop сообщает «Магазин временно
закрыт». Все навигации и buy/sell/redemption проверяют состояние в SQLite до денег.
При гонке сделка целиком завершается раньше остановки или отклоняется после неё.
Повторная остановка безопасна; CSV build/publish магазин не включает.
Для совместимости прежний магазин без новой строки состояния работает по старому
контракту до явного stop/create: миграция сама его не отключает.

## Восстановление создания и несколько тем

/shopcreate работает в worker thread под EX catalog lock. Сначала currency
preflight и проверка всего кандидата в SAVEPOINT с откатом, без новых предметов.
Затем durable intent (BLOB <=32 MiB, хеш, scope, план) фиксируется в SQLite.
Только после этого atomic replace/fsync runtime. Вторая BEGIN IMMEDIATE повторно
проверяет валюты, выполняет sync, включает состояние и удаляет intent одним commit.
Чужие темы сохраняются из прежнего runtime, их offers не обновляются автоматически.

Сбой до/после замены оставляет intent; торговля общим каталогом fail-closed.
Администратор той же темы повторяет /shopcreate с тем же режимом: проверяются
хеш/мастер/план/валюты, публикация завершается без дублей. Не удалять intent,
не править SQLite, не подменять кандидат вручную. Если исходники/валюты изменились,
нужно отдельное рассмотренное восстановление. /stopshop посреди создания отменяет
автоматическое включение; нужен новый явный /shopcreate. Ожидающую публикацию
другой темы её соседний topic admin не завершает. Общий runtime означает общую
fail-closed границу при его повреждении или незавершённой публикации.
Порядок lock → SQLite сохраняется. /stopshop берёт только SQLite, файлового lock
после неё не запрашивает; циклического ожидания нет.

Дополнительный Telegram TEST чеклист после согласования финального SHA:

1. Оба режима, точные примеры 3500→99.75/0.9975, максимум, реальные базовые единицы.
2. Ошибки валют/монетной обычной вещи до импорта, отсутствие offers, только ручные покупки.
3. Два thread одного чата: -b/-m; новая тема не меняет соседнюю; остановить только одну.
4. Повторный stop, restart, старые buy/sell/обмен callback, /shop закрыт, гонка с покупкой.
5. Повторный create сохраняет credit/sold/историю; смена режима отклоняется.
6. Известная вещь вне offers продаётся; неизвестные/неоднозначные/валюты скрыты и отклоняются.
7. CalculationLimit выплаты → вся точная сумма в credit; ошибки целостности → rollback.
8. Credit+монеты в обоих режимах, повтор/restart обмена; невозможность не меняет баланс.
9. Сбой до/после replace, повтор create, audit/FK/integrity и отсутствие дублей.
10. Повторить все прежние Telegram и Mini регрессионные сценарии, записать SHA/результаты.

## Безопасный откат приложения, каталога и настроек

Откат каталога — validate→publish сохранённой версии с её мастером и текущими
факторами тем; индекс, настройки, sold и история сохраняются. Подмена -b/-m
или единицы credit каталогом запрещена. После новых операций нельзя заменять
текущую SQLite старой backup и удалять новые таблицы.

До обсуждения отката: /stopshop во всех действующих темах, audit, online backup
SQLite с WAL, согласованный снимок master/map/offers/runtime/settings и хеш-манифест.
Read-only gate с точным целевым commit:

~~~bash
python -m app.dnd_shop.cli rollback-check \
  --target-ref d9856b2038a36490f93a4f5613ba7887698ac7e8 \
  --db /PATH/TO/ISOLATED/COPY.db
~~~

Без target-ref отказ. SHA96ff/SHA6165 имеют /shop, игнорирующий новый enabled:
откат блокируется даже с enabled=false и нулевым credit. /stopshop не является
техническим отключением старого приложения. Непроверенные цели запрещены.
Gate допускает явно проверенные версии без обычного магазина 5e4d4495/d9856b20
либо идентичное текущему HEAD дерево app с теми же контролями торговли
(нормализация CRLF допускается при проверке локальных исходников). Перед этим все
известные scope остановлены, публикации завершены. Для версии без магазина
ненулевые обязательства остаются в текущей БД/аудите до возвращения совместимого
кода; старое приложение их не погашает. Старый startup доказывает совместимость
структуры данных, но не безопасность старого торгового интерфейса.

Защищённый deployment bundle не изменён и автоматически этот gate не вызывает.
Это обязательный отдельный ручной preflight, а не защита от обхода deploy другими
средствами. Если требуется принудительное автоматическое отключение старого /shop,
это блокер релизной процедуры до отдельного согласования deployment/внешней
технической блокировки. Самостоятельного обхода нет. Автоматического rollback нет.
Любое выполнение — отдельное решение владельца. PROD deploy только после ревью,
полного CI/TEST финального SHA, согласованного merge/preflight/backup и разрешения.
Три PvP gate, protected FD, CRLF/EOF/Ctrl+C и порядок служб helper сохранены.
