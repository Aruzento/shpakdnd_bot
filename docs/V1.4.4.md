# V1.4.4 — магазин обычного D&D

Реализация относится к обычному D&D. `app/mini/`, его кошелёк, магазин,
инвентарь, гача и контент не изменяются. База ветки:
`5e4d4495a189380542cc643c5c8d723b9351b36b`.
Версия требует независимого ревью ChatGPT, зелёного CI и реального Telegram
тестирования точного финального SHA. Эта инструкция не является разрешением
на merge, установку на TEST или production deployment.

## Файл и настройка

По умолчанию `DND_SHOP_CSV_PATH=/var/lib/shpakdnd/shop.csv`; задаётся в окружении
процесса бота / его существующем `.env`. Смена самого пути требует перезапуска;
правки содержимого CSV — нет. Рабочий CSV и соседний `shop.csv.lock` находятся
вне checkout, app, watcher и Git. Пути через симлинк внутрь checkout отклоняются.
Новый каталог кода `app/dnd_shop` добавлен в watcher; внешний CSV туда не входит.

Пример (демонстрационный, не production ассортимент):

```csv
chat_id,thread_id,code,name,description,price,stock,active
-5320347021,0,short_sword,Короткий меч,Обычный короткий меч,100,5,true
-5320347021,0,healing_potion,Зелье лечения,Восстанавливает здоровье,50,10,true
-5320347021,0,rope,Верёвка,Прочная верёвка,20,3,true
```

UTF-8, допустим BOM; обязательны все восемь колонок. В одной теме уникальны
и SKU, и имя без учёта регистра. `code` — 1–80 ASCII букв, цифр, `_`, `-`.
Имя — до 100 символов, описание — до 1500. Цена — положительная конечная
десятичная строка до 40 символов, без экспоненты; `stock` — целое от 0 до
2^63−1, `active` — true/false. До 5000 строк и 2 MB на файл.
Проверяются все темы файла, конфликт с валютой, соответствие реестру и Mini.

`code` постоянно связан с `dnd_items.id`. Он никогда автоматически не
переназначается. Смена `name` меняет подпись предложения, сохраняя первоначальный
предмет и его имя в инвентарях. Имя существующего другого предмета запрещено.
Чтобы завести **другой** предмет, нужен **новый code**; для переназначения старого
нужна отдельная рассмотренная миграция. Изменение описания CSV меняет карточку,
не переписывая исторические описания инвентарей.

`stock` — суммарный лимит покупок за всё время SKU. Доступно
`max(0, stock - sold)`. Чтобы пополнить магазин, увеличьте лимит; уменьшение
ограничивает следующие покупки. Удаление и возвращение code не стирает sold.
Выкуп у игрока не увеличивает остаток. `stock=0` запрещает покупку, но допускает
выкуп. `active=false` запрещает оба направления торговли.

## Публикация без restart

Каталог и lock-файл должны быть доступны пользователю службы для чтения/записи.
Публикацию выполняет тот же системный пользователь; каталог не должен быть
доступен на запись посторонним. Убедитесь, что `shop.csv.lock` не удаляют и не
заменяют между операциями. Путь CSV должен быть локальной файловой системой
с поддержкой flock и атомарного rename; не NFS/SMB.

1. Подготовьте временный файл `/var/lib/shpakdnd/shop.next.csv`.
2. Из проверенного checkout, с Python окружения бота и настроенным BOT_TOKEN:

```bash
.venv/bin/python -m app.dnd_shop.cli validate /var/lib/shpakdnd/shop.next.csv \
  --target /var/lib/shpakdnd/shop.csv --db /PATH/TO/CONFIRMED/SQLITE
.venv/bin/python -m app.dnd_shop.cli publish /var/lib/shpakdnd/shop.next.csv \
  --target /var/lib/shpakdnd/shop.csv --db /PATH/TO/CONFIRMED/SQLITE
```

Не подставляйте production SQLite при настройке TEST. Валидатор не создаёт БД.
Он проверяет связь с реестром в транзакции, откатывая проверочные записи.
Publisher создаёт файл в том же каталоге, fsync, получает эксклюзивный
`shop.csv.lock`, повторно валидирует реестр, делает `os.replace`, fsync каталога
на Linux, освобождает lock. Права действующего файла сохраняются, для первого
файла — 0640; временный файл удаляется и при отказе.

Все операции торговли: **shared lock каталога → SQLite BEGIN IMMEDIATE →
проверки/расчёт/запись → COMMIT или ROLLBACK → освобождение lock**.
Publisher использует тот же порядок с exclusive lock. На Windows shared
режим эмулируется эксклюзивной byte-range блокировкой, поэтому читатели
последовательны. Нельзя брать SQLite lock, затем ждать lock каталога.
Нельзя оборачивать CLI в другой flock на этот же файл: CLI блокирует сам.

Свежий CSV читается при /shop, входе в списки, смене страницы, карточке и
подтверждении. При ошибке источник закрывает торговлю, старого кеша нет.
Главное меню / выход остаются доступны из открытого интерфейса даже при
повреждённом CSV. Удалённые/неактивные SKU не обслуживаются старыми кнопками.
Изменившаяся цена показывает новое предложение с новым токеном; необходимо
нажать ещё раз. Прямое неатомарное редактирование файла сторонним процессом
**не обеспечивает** согласованность с торговлей; используйте publisher.

Если CSV повреждён: исправьте candidate, проверьте валидатором и опубликуйте.
Не удаляйте историю, mapping, lock или SQLite; перезапуск не чинит CSV.

## Валюты и экономика

Источник номиналов — `dnd_items/dnd_currencies`, монет — `inventory`.
Создание валют остаётся через /admcoin и /admscoin. Используются активные
зарегистрированные валюты только текущей темы; активная базовая обязательна.

Номинал = `Fraction(Decimal(base_value)) / currency_quantity`.
Цена и 3% — Fraction, float/округлений нет. Алгоритм ограниченных сумм
оплаты использует двоичное разбиение количества монет;
точная оплата сначала ищется только до цены, без перебора всего богатого кошелька; для сдачи/выплаты —
неограниченный динамический размен. Сначала точная оплата, затем минимальная
переплата, затем минимум перемещаемых монет; остаточные равенства разрешаются
стабильным порядком ID/векторов. Нестандартные номиналы допустимы.
Торговец имеет виртуальную кассу зарегистрированных монет, без лимита запаса.
Списано − сдача = цена; выплата = цена × 3/100.

Ограничения расчёта: 32 активных номинала, 200000 достижимых сумм /
единиц сдачи, 2000000 шагов DP, 128 бит масштаба знаменателей.
Превышение — отдельная ошибка предела расчёта, не доказательство
невозможности размена. Если точная сдача или 3% недоступны, изменений нет.
Минимальной выплаты нет: 100→3; 50→1.5; 10→0.3; 1→0.03.

В продаже показывается собственный инвентарь, включая неизвестные торговцу
вещи; валюты исключены. Неоднозначные legacy-записи с item_id=NULL не
объединяются и не исправляются автоматически; однозначные разрешаются
по реестру и могут продаваться с сохранением NULL у оставшегося количества.
Некорректные количества и переполнение блокируют операцию целиком.

## Владелец, токены, история

При первом /shop Telegram ID связывается с подтверждённым username текущего
Telegram пользователя в конкретной теме. Это привязка при первом обращении,
поскольку исторический обычный D&D не хранит Telegram ID. Последующее
изменение ID/username блокируется; администратор должен отдельно проверить
личность перед рассмотренной миграцией `dnd_shop_owners`, а не удалить связь
для обхода. При отсутствии username, персонажа или при неоднозначности отказ.
Персонажи берутся из characters, затем существующего TOPIC_SETTINGS fallback.
Для кнопок повторно проверяются ID, username, чат, тема, снимок персонажа.

Сессии действуют 24 часа; выход закрывает сессию. Токены операций постоянны
в SQLite, цена и владелец не берутся из callback. Callback меньше 64 байт.
Повтор завершённой операции возвращает сохранённую квитанцию; ошибка
Telegram после COMMIT не повторяет сделку. Новое открытие карточки —
отдельное предложение; каждое подтверждение проводит один экземпляр.
При database is locked / занятом CSV — до 5 секунд ожидания и явная ошибка,
без автоматического повторного применения.

Аддитивная миграция `app/db/dnd_shop.py` вызывается из init_db и создаёт:

- `dnd_shop_skus`: постоянный SKU→item_id и sold.
- `dnd_shop_owners`: проверенная связь ID/username в теме.
- `dnd_shop_sessions`: владелец, персонаж, срок, закрытие.
- `dnd_shop_operations`: одноразовый токен, сторона, SKU/вещь, цена, квитанция.
- `dnd_shop_trades`: покупки и продажи с точными ценой/стоимостью TEXT.
- `dnd_shop_money`: фактические debit/change/payout, целое количество,
  снимок точного номинала TEXT (включая 1/3).

Существующие таблицы, публичные API и исторические данные не переписываются.
Одна SQLite транзакция содержит все монеты, вещь, sold, историю и токен.

Просмотр журнала (read-only на подтверждённом пути):

```bash
sqlite3 -readonly /PATH/TO/CONFIRMED/SQLITE \
  'SELECT id,created_at,kind,chat_id,thread_id,user_id,sku,quantity,price,value FROM dnd_shop_trades ORDER BY id DESC LIMIT 50;'
sqlite3 -readonly /PATH/TO/CONFIRMED/SQLITE \
  'SELECT trade_id,item_id,direction,quantity,denomination FROM dnd_shop_money ORDER BY trade_id DESC LIMIT 100;'
```

## Проверки

Новые тесты: `python -m unittest discover -s tests/v1_4_4 -q`.
Полный suite и все существующие валидаторы обязательны на финальном SHA:

```bash
python -m unittest discover -s tests -q
python check_bot.py
python -m compileall -q bot.py app
python -m app.mini.combat.hero_abilities.validate
python -m app.mini.boss.boss_abilities.validate
python -m app.mini.tower.validate
python -m app.mini.validate_v142
python -m app.mini.editorial.validator
python tools/validate_editorial_release.py
python tools/validate_pvp_migration.py
python tools/verify_editorial_mechanics.py
python tools/validate_dnd_shop_release.py
git diff --check
```

`tools/validate_dnd_shop_release.py` создаёт старую наполненную SQLite с
историческими INTEGER/REAL/TEXT/NULL, копирует её, повторяет миграцию,
проверяет DDL rollback, invariants, integrity/foreign keys и запуск старого
кода на мигрированной копии. Дополнительно
`--source /PATH/TO/CONFIRMED/COPY.db` открывает источник read-only и проверяет
его disposable backup; не модифицирует источник. Требуется отдельно
проверить **актуальную копию production** перед разрешением релиза.
Локальная историческая БД не выдаётся за актуальную production.
Linux release workflow сохраняет все старые проверки и добавляет CSV CLI,
миграции магазина и проверку отсутствия diff в app/mini.

## Production preflight и rollback

Merge/deploy запрещены без решения владельца. Порядок: feature → PR →
независимое ревью ChatGPT → финальные тесты/зелёный Linux CI → TEST Telegram →
повторная сверка финального SHA → согласованный merge → preflight →
отдельно разрешённый sudo deploy-shpakdnd → службы и Telegram.

До релиза: подтвердить отсутствие незапланированных изменений и секретов;
сделать согласованный backup SQLite и внешнего CSV, сохранить SHA/права/
владельца/пути; проверить миграции на актуальной копии production и old-code
startup; проверить восстановимость backup на отдельной копии; проверить
внешний lock, чтение каталога, watcher и готовность установленного deploy bundle.
Длительные проверки выполнить до остановки бота, обязательные повторные
проверки deploy не удалять.

Rollback только по отдельному решению владельца: остановить новые операции,
сверить последние trade IDs и backup; вернуть согласованный код на **текущей**
мигрированной SQLite (новые таблицы аддитивны), сохранить журнал V1.4.4.
Восстановление старой SQLite поверх новых операций не автоматизируется:
это уничтожит операции после backup. CSV откатывается через validate/publish
при сохранении mapping и sold. Если после ревью нужен remap SKU/owner,
подготовить отдельную миграцию с backup и сверкой журнала.

## Статус передачи на независимую проверку

Добавлены 49 тестов V1.4.4; существующие тесты не удалены, новые skip не
добавлены. На Windows у старого suite есть один прежний пропуск
`tests/v1_3_3/test_deploy_shell.py` (POSIX symlink semantics); Linux CI
должен выполнить его. Все проверки повторяются на финальном коммите;
точный SHA, итоговые числа и ссылки CI/PR сообщаются в отчёте PR.
Искусственные ошибки Telegram/PvP в тестовых логах — проверяемые сценарии
существующего suite, не обращения к Telegram и не production сбои.

Проверена read-only backup копия локальной исторической SQLite, а также
синтетическая старая схема с реальными SQLite типами INTEGER/REAL/TEXT/NULL.
Это не подтверждение свежей production копии. Реальное Telegram staging,
права пользователя службы на TEST/PROD, согласованный backup и релизное
ревью пока требуют оператора. Деплой и merge на этом этапе не выполняются.
