## 1. БЕЗОПАСНАЯ АРХИТЕКТУРА UI

- Сохрани существующий персональный ephemeral-подход Mini, публичными остаются лишь предназначенные для публикации анонсы/ходы. Не выдавай чужие экраны и ресурсы.
- При выводе экрана используй layout из соответствующего `id` дизайн-карты: количество строк, последовательность, подписи, `image`, условную видимость. Динамические кнопки формируй сервером.
- `actions` в JSON — описательные имена, НЕ исполняемый Python. `visible_if` — текстовое бизнес-условие, НЕ eval/код. Реализация строго через whitelist обработчиков и серверные проверки. `next_msg_id` — проектный screen ID, а не готовый Telegram callback.
- `callback_data` не больше **64 байт**. Не помещать сырые JSON, большие имена, цены/состояние/подписи или недоверенные идентификаторы в callback. Использовать короткие ключи, owner/scope, revision/operation token; при необходимости серверное хранилище.
- Для `ui_back`/`nav_back` держать доверенный previous-screen / parent / context с безопасным fallback и контролем существования состояния. «Главная» всегда `home`; «Назад» — на логический родительский экран, не в случайный `next_msg_id` исторического снимка.
- Для пагинации поддерживать устойчивые `page`, `page_count`, `hero_id`, `filter`, `selected_rarity`; проверять границы при изменении списка. Сохранять страницу/фильтр при входе в карточку и обратном переходе.
- Проверять владельца callback, Telegram user ID, принадлежность сущности, Mini topic, права admin, статус попытки, revision до мутации. Двойные клики/конкуренция/старые сообщения безопасны.
- При изменении предмета, героя или работника обновлять экран, не создавать цепочки публичных сообщений. Учитывать Telegram `message is not modified`, истёкшие/удалённые сообщения, фото-текст fallback.
- Не считать макет JSON готовой runtime-конфигурацией. Допускается реализовать layout существующими Python builders либо безопасным декларативным loader/renderer. **Нельзя** вводить исполняемые сценарии/SQL в UI JSON. Не включать небезопасное hot-reload на проде; если loader предложен, добавить schema validation, last-known-good, atomic reload, fail closed и интеграцию с watcher без неожиданного рестарта/отключения. Архитектура должна оставлять путь к будущему редактированию UI без вмешательства в экономику.
- Учитывать реальные ограничения цветов/стиля InlineKeyboardButton и поддерживаемую библиотекой/Telegram версию; `default/primary/success/danger` трактовать как пожелание макета с безопасным fallback.
- **Все 109 экранов** из приложения в конце этого файла должны быть учтены: 17 меняются целенаправленно; остальные сохраняют доступные действия, права, тексты и состояние, а не пропадают при рефакторинге.

## 2. ОБЯЗАТЕЛЬНЫЕ РЕШЕНИЯ ПО КОНФЛИКТАМ МАКЕТА И ПРЕЖНЕГО ТЗ

1. **Дома vs Жильцы.** По новой карте `village_houses`: «Купить», «Поселить» + «Выселить», навигация. По прежнему ТЗ требуется отдельный список жильцов 2×2 и карточка с ТРЕМЯ действиями. **Сохранить оба**: добавить в `village_houses` отдельной строкой кнопку **«👥 Жильцы»** перед строкой «Главная/Назад». Новый `village_residents` — строго 4 жителя (2×2) на страницу; новый/обновлённый `village_resident` — **«Снять с производства» / «Выселить» / «Назад»**. Убрать из карточки прямые кнопки назначения Шахта/Рынок/Охота. Старые callback обработать безопасно (показать обновлённый экран или отказать), не выполнять запрещённую смену работы.
2. **Перевод работника vs только безработные.** Новая карта для `<job>_add` показывает ТОЛЬКО поселенцев без работы (`building=None`). Не нарушать это. Перевод доступен в ДВА ШАГА: «Убрать» на прежнем предприятии или «Снять с производства» в карточке жильца, затем «Добавить» на новом. Никаких неявных переводов при выборе занятого героя. Это сохраняет возможность переназначения без конфликтов производственных слотов.
3. **Мифические герои.** Кнопки нет в `heroarea`; доступ обязательно через `more → mythic`. Кнопка «Назад» из Mythic должна возвращать в `more`, а не слепо в старый `heroarea`.
4. **Регистрация.** `registration` + `create_help` слиты в один экран; старый `created` удалён из новой навигации, но legacy callback не должен падать. После успешной регистрации открывается `home` с одноразовым сообщением и СУЩЕСТВУЮЩИМ стартовым подарком. `/minicreate` остаётся. Для кнопки безопасный персональный запрос имени — например, private-chat deep link / валидируемое состояние; не требовать от пользователя публично печатать имя в общей теме.
5. **Купон.** В старом макете есть абстрактный `gacha_coupon` с одной кнопкой «Применить». Реализовать реальный выбор из трёх типов купонов по количеству в инвентаре, затем «✅ Применить купон», затем стандартный `gacha_result`. Если купон одного типа, можно пропустить выбор, но подтверждение/безопасность сохранить. Купоны не являются обычными билетами и не меняют pity.
6. **10× призыв.** В UI-карте есть кнопки и batch-screen, но сервиса нет. Реализовать полностью: 10 последовательно симулированных стандартных круток в **одной атомарной транзакции**, результаты, pity, luck, дубликаты, разовая оплата и идемпотентность. Цена = **10 × актуальная стоимость одиночной платной крутки**, без новой скидки и без списания билетов, если другой механизм явно не установлен. Недостаток денег/пула → никакой части пакета.
7. **Башня.** Новая трёхшаговая навигация по редкости заменяет старые selector_* в интерфейсе; сохранить legacy callback-совместимость, не менять общий boss-selector. Во время активной попытки запретить смену героя. Кнопку «Повторить бой» реализовать через настоящий idempotent service retry, а не просто перерисовать `tower_lost`.
8. **Шардовый обмен.** `shards_sell` присутствует в карте, но переход к нему мог исчезнуть. Сохранить существующий доступ; если реально стал недостижимым — добавить контекстную кнопку «💱 Продать осколки» в `hero_card` (при доступных осколках), не удаляя кнопки макета.
9. **Назад/возврат.** Править исторические несоответствия макета: из `gacha_result` возвращаться к `gacha` или безопасному предыдущему экрану, из карточки коллекции — к конкретному исходному списку с фильтром/страницей (при наличии контекста), из `village_resident` — к странице жильцов, из Mythic — в `more`. Не оставлять без выхода экран игры, в том числе events или пустые списки.

### 3.4. Башня / Испытания

`tower` — stateful dispatcher (`tower_select`, `tower_ready`, `tower_active`, `tower_lost`, `tower_won`, `tower_completed`), **не показывать кнопки всех состояний сразу**. В состоянии выбора или готовности: `[🎴 Выбрать героя][🛡 Экипировка]`, затем `[⚔️ Начать бой]` при возможности, внизу `[🏠 Главная][⬅️ Назад]`. В активном бою — `[⚔️ Атаковать]`, доступный безопасный просмотр экипировки, Главная/Назад, **никакой смены героя**. Переодевание при активной попытке не должно менять snapshot бонусов.

Новый выбор:
```
tower_select (выбрать РЕДКОСТЬ, до 2 кнопок в строке)
  → tower_heroes_by_rarity (до 6 героев на страницу, 2 в строке; ◀/page/▶)
    → tower_hero_card (ОДНА карточка + изображение + контрпики)
```
В `tower_hero_card`: `[✅ Выбрать этого героя]` → остаёмся в карточке, после выбора `[✅ Герой выбран]`; `[◀️ Предыдущий][Следующий ▶️]`; `[🏰 К испытанию][⬅️ К героям]`; `[🏠 Главная]`. Проверять доступность жителя/занятость в другом бою и принадлежность героя на момент сохранения, а не только на выводе.

`tower_lost`: `[🔄 Сменить героя][🛡 Экипировка]`, `[🔄 Повторить бой]`, `[🏠 Главная][⬅️ Назад]`; retry — реальный безопасный переход/новая попытка с проверкой правил без повторной награды. `tower_won`, `tower_completed`: сохранить экран и награды с единичной финализацией. `tower_selector_*` legacy оставить для корректного завершения старых callback, без новых входов. Не трогать режим selector для Boss. ## 8. ГАЧА — ГАРАНТ 10 / 25 / 85 И ПРИЗЫВ ×10

### 8.1. Три независимых счётчика каждого Mini-игрока

- Каждая **10-я стандартная крутка без Uncommon** обязана выдать `uncommon`.
- Каждая **25-я стандартная крутка без Rare** обязана выдать `rare`.
- Каждая **85-я стандартная крутка без Legendary** обязана выдать `legendary`.
- Досрочное выпадение **точно соответствующей редкости** сбрасывает ТОЛЬКО её счётчик в 0. Rare не обнуляет Uncommon; Legendary не обнуляет Rare/Uncommon.
- Каждая крутка выдаёт ОДНОГО героя, не дополнительную награду сверху.
- При одновременных готовых гарантиях приоритет **Legendary > Rare > Uncommon**. Более слабые готовые гарантии ПЕРЕНОСЯТСЯ до следующей доступной стандартной крутки, не теряются. Счётчик достигает порога и остаётся насыщенным (10/25/85), без переполнения. Пример совпадения трёх: Legendary, затем Rare, затем Uncommon (если не было промежуточных совпадений). Порядок фактических выпадений всегда обновляет соответствующие счётчики.
- Если нет принудительного гаранта, применять действующие базовые шансы 69/25/5/1 (или фактические актуальные, с действующими модификаторами luck); не менять цену и баланс.

Учитывать ТОЛЬКО стандартные монетные крутки и стандартные крутки через обычные билеты. НЕ учитывать купоны целевой редкости, награды, админ-выдачи, Shadow, Mythic, компенсации. Получение Legendary по купону НЕ сбрасывает pity.

Существующие административные гарантии и зелья удачи сохраняют свою логику. Если административная гарантия реально выдаёт Legendary в стандартной крутке, сбросить Legendary pity, но не выдать второго героя. Не использовать административный forced flag как счётчик нового pity.

Хранить, например, в `mini_gacha_pity(player_id UNIQUE, uncommon_count, rare_count, legendary_count, updated_at)`; существующие игроки без записей стартуют с 0, без недостоверного восстановления по истории. `CHECK` и транзакции, SQLite restart/persistence.

В `gacha` отображать:
```
🎴 Гарант призыва
🟢 Необычный: 6/10
🟣 Редкий: 14/25
🟡 Легендарный: 37/85
```
Для насыщенного значения — «Гарант готов». Показывать прогресс после каждой операции. Не публиковать обновления в общую тему.

### 8.2. Стандартный призыв ×10

Новая кнопка — реальная операция 10 последовательных стандартных круток за монеты с фиксированной полной ценой на момент начала: `10 * effective_single_pull_price` (если текущие правила цены динамические — корректно вычислить и зафиксировать итоговую стоимость перед списанием, не менять существующий баланс). Без отдельной скидки и без списания обычных билетов. Проверить достаточность монет и доступность пула ДО начала. Все 10 результатов обрабатываются тем же сервисом, что одиночный призыв, с sequential pity и действующими эффектами удачи по их фактическому сроку/зарядам. Дубликаты, осколки, автоактивация и статистика не теряются.

**Атомарность:** списание полной суммы + 10 героев/осколков + 10 шагов pity + расход luck + журнал `operation_id` фиксируются в ОДНОЙ транзакции. На сбое не сохранять частичные результаты. Не держать внешние Telegram операции внутри транзакции. После commit показать результаты из сохранённого immutable batch. Повторный callback того же действия только перечитывает результат; кнопка «Ещё 10» должна создавать НОВУЮ уникальную операцию через свежий подтверждённый пользовательский action, а не дважды выполнять старую. На одном и том же старом сообщении повтор не должен вызывать бесконечные покупки.

Результат списка из десяти должен иметь доступ к каждому герою и листанию; при отсутствии средств/героев batch целиком отклоняется. В каждом пакетном ролле проверить пересечения pity: например, получение Rare на 25-м счётчике и переход Legendary 85 в середине десятки.

### 8.3. Обычные крутки и купоны

## 10. ВАЛЮТЫ ОБЫЧНОГО D&D — ПРЕДМЕТЫ И НОМИНАЛЫ

Команды глобального администратора:
```
/admcoin CHATID:THEMEID "Золотая монета" 1
/admscoin CHATID:THEMEID "Медная монета" 1 = 0.01
/admscoin CHATID:THEMEID "Серебряная монета" 1 = 0.1
/admscoin CHATID:THEMEID "Платиновая монета" 1 = 10
```

`/admcoin` создаёт **первую и единственную базовую валюту** конкретного `(chat_id,thread_id)` с номиналом 1 и определение предмета `currency`. Повторная базовая валюта запрещена. `/admscoin` создаёт дополнительную валюту, где `X новых монет = Y базовых`, `value_per_coin = Y / X` точно по `Decimal`/rational и строковому/целочисленному точному хранению. **Никакого float**. К примеру 1 платиновая = 10 золотых = 100 серебряных = 1000 медных.

Добавить `dnd_currencies`, связать через `item_id` с `dnd_items`, хранить `base_value`, `is_base`, дату; обеспечить единственную базовую на scope, положительный номинал, FK, уникальность и отсутствие двусмысленных названий. Номинал задан относительно базовой валюты — автоматического обмена сейчас нет.

Валюты — реальные предметы в стандартном D&D-инвентаре:
```
/admadd CHATID:THEMEID @username Золотая монета x15
/admadd CHATID:THEMEID @username Серебряная монета x50
/admadd CHATID:THEMEID @username Медная монета x120
```
`/inv` показывает имена и количества; `/admdel` удаляет. Само определение валюты никому её НЕ выдаёт. Не создавать отдельный кошелёк. Не смешивать Mini-монеты и D&D-инвентарь.

Проверить право global admin, валидный scope с учётом чатов без тем, `topic_guard` и запрет регистрации в Mini-теме; парсинг кавычек, X положительное целое, Y положительное конечное decimal, нет `NaN/Infinity`, пустых имён/дублей, SQL injection/параметризация. Все этапы создания одной валюты транзакционны и безопасны при повторе.

**Магазин обычного D&D сейчас НЕ реализовывать.** Подготовить возможность в будущем привязать цены/валюту оплаты, покупки/продажи, журнал и транзакционное списание инвентарных монет; без новых торговых экранов, автоматического обмена или банковской системы.
