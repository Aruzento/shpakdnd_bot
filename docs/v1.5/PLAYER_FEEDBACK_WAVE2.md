## Что установлено и что не доказано

Подтверждён путь ошибки SDK: Message.delete_ephemeral() требует receiver_user, которого может
не быть у callback Message. Прямой Bot.delete_ephemeral_message использует уже проверенного actor.
Старое окно деактивируется в SQLite до отправки нового; Telegram-ошибка или поздний ответ старой
генерации его не оживляет. Токены callback не удлиняются (64 bytes сохранены).
После неизвестного результата отправки предлагается вновь открыть публичный launcher или /mini.
Публичные сообщения не редактируются в личные и не удаляются журналом.

Смена героя вызывает только личный send_hero_card. Публичная карточка отправляется отдельным явным
«Поделиться». Сообщение Т2 само по себе не доказывает утечку: для вывода нужен реальный скриншот
с двух клиентов. Отказ удаления воспроизведён синтетически; новый UX требуется проверить на TEST
после отдельного разрешения владельца. SDK/Telegram может оставить физическое старое окно,
но его личные callback после нового окна сервер отвергает и после перезапуска.

Холодный JSON/PNG raid validation не ускорен за счёт ослабления: полная проверка переносится до
polling, затем используется content-hash cache первой волны. Новые метрики охватывают mini:launch,
home и gacha. Dispatcher не знает время создания callback на стороне Telegram.
Синтетические измерения отдельно от реальной API-сети; новый кандидат на TEST не запускался.

## Диагностика гачи без изменения баланса

Существующие базовые веса: Common 69%, Uncommon 25%, Rare 5%, Legendary 1%.
Только четыре редкости обычного призыва; Mythic и Shadow исключены.
Тест 30000 выборов с seed 20261027 проверяет фактический picker и все доли в пределах 6σ.
Это тест базового распределения без pity, а не обещание 1% среди всех итоговых призывов.
Pity — независимые счётчики точной редкости: 10/25/85; сбрасывается только выпавшая точная
редкость, одновременно достигнутые гарантии разрешаются Legendary → Rare → Uncommon.
Ручная гарантия Legendary расходуется существующим сервисом. Пакет — 10 последовательных
операций с теми же гарантиями и результатами, один транзакционный receipt.

Дубликат начисляет базовые осколки × прежнее количество копий и увеличивает copies на один:
базы 10/20/40/100. Поэтому 90 осколков Common при 9 прежних копиях — действующее правило,
а не доказательство бага. Накопленные копии отображаются в карточке, суммарные осколки —
в пакете. При отсутствии pity шанс не получить Legendary за 30 выборов примерно 74%;
pity ограничивает длинные серии. Оснований менять утверждённый баланс из этих наблюдений нет.

## Административные TEST-ресурсы

Выполняет только владелец Mini с configured SUPERADMIN_USER_ID, после проверки TEST bot identity.
Подставить реальный Telegram user ID; не отправлять эти команды production-боту.

    /superlook -1003883723333:2 USER_ID -c -s -p -i
    /superadd -1003883723333:2 USER_ID -c 300
    /superadd -1003883723333:2 USER_ID -i summon_ticket
    /superadd -1003883723333:2 USER_ID -p Villager
    /superlook -1003883723333:2 USER_ID -c -s -p -i

Каждая item-команда выдаёт один предмет. -p использует реальный code из каталога; не выдавать
несуществующих персонажей. Mythic получают игровым путём при обычной приёмке.
Один operation key super:chat_id:message_id защищает повтор доставки того же сообщения;
новое сообщение с тем же текстом является НОВОЙ выдачей. Не копировать команду повторно
после неопределённого ответа: сначала посмотреть audit и остаток.

Read-only на приватной копии SQLite:

    SELECT * FROM mini_superadmin_audit ORDER BY id DESC LIMIT 20;
    SELECT * FROM mini_wallet_transactions ORDER BY id DESC LIMIT 20;

Канонические сервисы — app/mini/wallet.py и superadmin/service.py. Никаких SQL UPDATE для выдачи.
Инструкция не означает, что ресурсы уже выданы; в этой итерации выдач на TEST нет.

## Данные и откат

Аддитивные CREATE TABLE IF NOT EXISTS: mini_private_windows, story_publication_parts,
story_reminders, story_achievements. Старые таблицы/строки/индексы не удаляются и не переписываются.
story_steps остаётся источником посещений всей группы. Ретроактивная выдача достижений за старые
прохождения не выполняется. Выплаты выключены конструктивно: новый код не вызывает wallet.

Frozen guard знает точные колонки новых опциональных журналов. Старый V1.5 target с их состоянием
получает BLOCKED_FEEDBACK_STATE_UNSUPPORTED; новые capability нельзя самовольно добавлять
в audited allowlist. sending/uncertain напоминания дополнительно требуют ручной проверки доставки.
Для повторного запуска нужен проверенный новый SHA/APP_TREE, policy, launcher и manifest;
обход проверок запрещён. См. TEST_CANDIDATE_SWITCH.md. TEST/production не переключались.
