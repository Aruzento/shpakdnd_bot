## I. Характеристики четырёх боссов

| Параметр | Босс №1 | Босс №2 | Босс №3 | Босс №4 |
|---|---|---|---|---|
| Уникальная механика | Циклическое разрушение брони | Периодическое приземление | Восстановление после 15 атак | Четыре защитные фазы HP |
| `max_hp` | `100000` | `115000` | `130000` | `150000` |
| `element` | `fire` | `lightning` | `dark` | `star` |
| `counter_elements` | `["ice"]` | `["star"]` | `["sun"]` | `["moon"]` |
| `features` в начальном snapshot | `["armored"]` | `["flying"]` | `[]` | `["armored", "flying"]` |
| `regeneration_percent` существующего движка | `0` | `0` | `0` | `0` |
| Фонд обычной победы R09 `ceil(original_max_hp/5000)` | `20` | `23` | `26` | `30` |
| `shadow_extractable` | `false` до авторской явной Shadow-цели | `false` | `false` | `false` |
| `counter_policy` | `first_confirmed_counter_hero_attack_on_this_raid` | то же | то же | то же |

Эти стихийные сочетания — выбранный набор **одной** контрстихии на каждого босса; остальные четыре Mythic-стихии не обесценены — остаются своими бафферами/источниками эффектов. Контрстихия активирует 100% вместо 10% для команды только после первой подтверждённой атаки соответствующего героя, в том числе с фактическим нулевым уроном, как уже утверждено O02. Первая соответствующая атака получает 100% **до** проверок дальности, брони и фактического HP damage. Наличие героя в коллекции само по себе не активирует контрпик.

### Босс №1 — разрушение брони

- Изначально `armored` действует на атаках с порядковыми номерами **1–10**.
- После десятой подтверждённой атаки броня разрушается: атаки **11–15** обрабатываются **без** `armored`.
- После пятнадцатой атаки броня восстанавливается; атаки **16–25** снова защищены, **26–30** — без брони, и так далее: цикл `10 armored + 5 unarmored`.
- Ведётся счётчик именно **подтверждённых списанных попыток Raid**; нулевые HP-попадания, включая недостижимые по `flying`, учитываются. Дополнительные события HP в рамках одной атаки **не** увеличивают счётчик.
- Переход случается **после** обработки десятой/пятнадцатой атаки и влияет со следующей. Не изменять базовый тег в JSON или frozen snapshot, только эффективную защиту отдельной атаки.
- Audit/UI: событие «броня разрушена / восстановлена», до следующего переключения атак. Реальный урон и противодействие Солнечного Mythic не менять вне эффективного тега.

### Босс №2 — воздушная фаза

- Изначально действует `flying` на атаках **1–8**. Атаки **9–10** — приземление, тег `flying` временно выключен.
- С 11-й атаки снова `flying` для следующих восьми, затем две атаки на земле. Цикл `8 flying + 2 grounded`.
- Пока босс летает, сохраняется действующая логика: обычные ближние атаки без `special_trait=flying` не достигают цели. Дальние и допускаемые полётные атаки работают по текущим правилам.
- Нулевые подтверждённые атаки тоже продвигают фазу (иначе команда без дальнобойных не сможет опустить босса). Контрстихия Star активирует O02 даже при нулевом actual HP, но **не отменяет физическую недосягаемость** `flying`.
- Переход после восьмой/десятой атаки влияет со следующей; журнал и Telegram показывают «в воздухе / на земле» и оставшиеся атаки фазы.

### Босс №3 — периодическое восстановление

- Отсутствует постоянная регенерация `regeneration_percent`: только уникальный триггер **после каждого 15-го подтверждённого Raid-удара** (15, 30, 45, ...).
- Размер восстановления: **`floor(original_max_hp * 25 / 10000)`**, то есть **325 HP** при 130 000 HP (0,25% исходного максимума).
- Ограничение: восстановить не более `max_hp - current_hp`, не воскрешать босса при `current_hp=0`, не начислять отрицательное восстановление.
- Если на этой атаке действует подавление регенерации от Солнечного Mythic, уникальное восстановление **отменяется**. Счётчик всё равно доходит до 15, переносить накопленное исцеление нельзя.
- Следить, чтобы текущая логика Sun (`sun` charges) в `effects.resolve` правильно учитывала её активность **на момент выполнения этой атаки**; эффект, полученный только по результату этого удара, не должен ретроактивно подавлять прошлое исцеление, но может подавлять последующее по контракту Sun.
- Повторы callback и дополнительные HP-события не дают добавочного лечения. Журнал отражает 325/фактическое исцеление либо подавление Sun.

### Босс №4 — защитные фазы

- Замороженная база порогов — `original_max_hp=150000`, **не** увеличивается из-за Eclipse, **не** пересчитывается при обычных исцелениях.
- Фаза 1: `current_hp > 112500` — эффективны оба тега `armored` и `flying`.
- Фаза 2: `75000 < current_hp <= 112500` — только `armored`.
- Фаза 3: `37500 < current_hp <= 75000` — только `flying`.
- Фаза 4: `0 < current_hp <= 37500` — ни одного защитного тега.
- Эффективная фаза выбирается по HP **на начало подтверждённой атаки**; пороги, пересечённые этой атакой (включая дополнительные HP-события), меняют защиту **со следующей атаки**. Пересечение сразу нескольких порогов переводит в соответствующую последнюю фазу один раз, с подробным audit.
- **Фаза монотонна**: исцеление, Eclipse или восстановление HP не возвращают босса в более раннюю защищённую фазу. По достижении HP=0 обычная завершённая победа, фазовые события не оживляют босса.
- В течение одной атаки все её эффекты защищаются состоянием фазы, замороженным на её начало, если только уже существующая отдельная пассивка явно не пробивает защиту.
- Telegram отображает фазу, активные защитные теги и следующий HP-порог.

## II. Контракт JSON, который нужно реализовать

Сейчас `app/mini/mythic/raid/catalog.py` допускает только статические `features` и обычный `regeneration_percent`. В `app/mini/mythic/raid/effects.py` нет переключений брони/полёта, периодического исцеления и HP-фаз. **Добавить строго типизированное поле `mechanic`**; не класть непроверенные произвольные поля.

Рекомендуемый минимальный контракт (допустимо скорректировать имена полей для чистоты проекта; семантика выше обязательна):

```json
{
  "mechanic": {"type": "armor_cycle", "armored_attacks": 10, "exposed_attacks": 5}
}
```

```json
{
  "mechanic": {"type": "flight_cycle", "flying_attacks": 8, "grounded_attacks": 2}
}
```

```json
{
  "mechanic": {"type": "periodic_heal", "every_attacks": 15, "heal_bps_of_original_hp": 25, "sun_suppresses": true}
}
```

```json
{
  "mechanic": {"type": "hp_defense_phases", "threshold_percent": [75, 50, 25], "phase_features": [["armored", "flying"], ["armored"], ["flying"], []], "threshold_base": "original_max_hp", "monotonic": true}
}
```

**Это фрагменты, а не готовые Boss records.** Не писать `name`, `code`, `image`, биографии, свойства Shadow и реальные boss entries от себя. В production-каталоге до поставки авторских записей сохраняется пустое / отсутствующее состояние и явный `BLOCKED_BY_INPUT`. Запретить неизвестные `mechanic.type`, лишние поля, отрицательные/нулевые периоды, неправильные пороги, неразрешённые `features`, ошибки типов (`bool` вместо `int`), неизвестные контрстихии и отсутствие четырёх записей при непустом каталоге.

## III. Архитектура и совместимость

1. На `start()` рейда **замораживать** валидированную спецификацию механики в `mini_mythic_raids.snapshot_json`; динамику хранить в `state_json`/существующей базе, чтобы перезапуск, смена каталогов и публикация новых файлов не меняли текущий рейд. **Если дополнительных колонок не требуется — не выполнять лишнюю миграцию.** Если миграция необходима, она только аддитивная и идемпотентная, с проверкой старых данных.
2. В одной SQLite-транзакции `attack()` отсчитывать **ровно одну** подтверждённую атаку, определять защиту на её начало, проводить обычный raid attack + все авторские/passive HP-events, применять завершающий эффект механики и единожды фиксировать state, damage, attack ledger, raid revision, rewards/end. При исключении откатывать **всё**; повтор операции возвращает сохранённый результат.
3. Порядок: validate actor/world/hero/operation/day → freeze effective phase/counter for attack → apply O02 counter matching **до HP-damage** → base damage and typed hero effects with effective features → post-hit periodic effects, if any → count/switch phase for **next** attack → atomic logs and finalization. Сохранять legacy O02 counter policies для ранее начатых рейдов.
4. Не менять статические `features` в снимке: вычислять `effective_features`, а `regeneration_percent` оставить совместимым (для четырёх этих новых боссов он `0`). Не выполнять двойное исцеление. Sun/armor bypass/flying reachability работать на динамической защите.
5. Реально нанесённый HP damage остаётся `0 <= actual <= HP_before` с корректной атрибуцией; **исцеление не уменьшает записанный положительный вклад**, не создаёт повреждения и не изменяет награду задним числом. При победе R09 использует `original_max_hp` (пулы 20/23/26/30), O01 использует утверждённый исходный фонд/фактические вклады, без награды за регенерацию или переход фазы. Не допустить переполнения SQLite `int64`.
6. Бои старых версий и текущие активные рейды без `mechanic` должны продолжаться **в точности по старому snapshot-контракту**. Новые механики только для новых боссов/новых рейдов. Отсутствие записи о механике не означает ошибку для старого рейда.
7. Telegram: на карточке рейда показывать реальную активную механику, состояние/счётчики, активные теги, текущую фазу или следующий порог. Не выводить выдуманное имя. Caption/text соблюдать UTF-16; устаревшие callback/публикации не дублируют награды/атаки.
8. 10 атак/игрок/сутки по Europe/Moscow, герой один раз/день на рейд, любые подтверждённые атаки (даже 0 урона) списывают попытку, кроме явно отклонённых команд/rollback; один активный рейд на мир, история, награды R09/O01, отдельные `normal`/`raid`, дети/питомцы/Tower/D&D-магазин/PvP не ломать.
9. Content importer/assets НЕ менять без необходимости. PNG четырёх рейдовых боссов и авторские коды/имена/записи владелец предоставляет отдельно; не создавать фейковых PNG, имён, персонажей, гача-героев. Не импортировать S5 в этой задаче без отдельного распоряжения.
