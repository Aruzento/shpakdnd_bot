## Отсутствие повторов и тупиков

Пусть V — объединение текущего node_id и концов подтверждённых story_steps этой session_id.
Удаляем V из frozen графа; обратным поиском от настоящих end:true получаем множество R
всех вершин, из которых есть путь к концовке. Разрешён выбор ровно тогда, когда next в R.
Путь в конечном графе всегда содержит простой путь: циклы можно убрать без изменения
концовки. Поэтому после выбора x существует простой путь x→…→end, не содержащий V.
После commit блокируется также x, но оставшийся суффикс этого пути остаётся доступным.
По индукции каждый активный неоконечный шаг имеет хотя бы один выход; |V| строго растёт,
повтор невозможен, прохождение заканчивается максимум за число вершин frozen графа.
Это доказательство относится к валидному snapshot и журналу; повреждённые данные
останавливают голосование диагностикой, не создают выдуманный финал.

visited_nodes, проверка голоса, tally, выбор при ничьей, story_steps, session и publication
работают в одной BEGIN IMMEDIATE транзакции. PK(session_id,step), operation_key и step
не позволяют дважды подтвердить переход; повтор ключа возвращает сохранённый результат.
Разные ключи последнего голоса сериализуются: поздний получает stale-step. Внешний файл
после start не участвует. Рендер использует вычисленные в status исходные индексы,
handlers декодирует исходный индекс, service ещё раз проверяет доступность ID в SQLite.

## Публикация и предел гарантии Telegram

story_publications фиксирует один claim на session/step. Pending current step можно
восстановить; sending после crash становится uncertain и автоматически не повторяется.
Невозможно атомарно подтвердить SQLite commit и доставку Telegram: при uncertain нужна
ручная сверка сообщения. Это существующая политика против дублей, а не обещание exactly-once
доставки внешнему API. Старые сообщения могут оставаться в чате; callback step делает
их неактивными, refresh пытается убрать старую клавиатуру. API failures журналируются.

Реальный Telegram staging/production DB copy пока не выполнены; готовность production
не подтверждена. Итоговый SHA и результаты Windows/Linux сохраняются в отчёте и draft PR,
чтобы после финальных проверок не менять сам проверенный коммит.
