# V1.4.4: операторская подготовка валют production, тема 4

Это план для отдельного решения владельца после ревью и CI. Он ничего не
применяет. Область: только обычный D&D, чат -1003376315265, тема 4.
Тема 3, Mini, TEST и ассортимент не активируются. Production SQLite, номиналы
и кошельки автоматически не изменяются.

## 1. Проверка исходного состояния

Production baseline: 5e4d4495a189380542cc643c5c8d723b9351b36b.
База этой доработки: f727e15652420ac851c0f17663e4c31bfd943b68.
Перед будущими действиями сверить hostname VM-436996, фактический SHA, clean
checkout, WorkingDirectory/User/PID службы и актуальный backup. Снимок для
ревью открывать только read-only; миграции/startup выполнять на новой копии.

Три существующие основные монеты должны быть активными записями category=currency:
золото — база 1, серебро — 1/100, медь — 1/10000 золотой.
Номинал проверяется как Fraction(Decimal(base_value))/currency_quantity.
Названия нужны для сопоставления с явным списком источника; сами по себе они
не подтверждают номинал или право использования code.

Из проверенного checkout на изолированном окружении:

~~~bash
python tools/inspect_dnd_shop_currencies.py \
  --source /PRIVATE/fresh-production.sqlite3 \
  --chat-id=-1003376315265 --thread-id=4 --allow-missing \
  > /PRIVATE/topic4-before.json
~~~

Инструмент открывает существующий файл mode=ro, query_only, BEGIN; не вызывает
init_db, регистрацию, выдачу монет или публикацию CSV. Выводит SHA-256 источника,
реальные item_id/code, точные номиналы, конфликты и недостающие позиции.
--allow-missing разрешает только отсутствие связок, не отсутствие основных
монет, ошибки номиналов, неактивные валюты или коллизии с обычными предметами.
При ошибке список команд регистрации пуст, применение запрещено.

## 2. Только ручная регистрация 12 отсутствующих позиций

После отдельного разрешения и backup существующий глобальный администратор
выполняет /admscoin (это права существующей административной команды).
Использовать только отсутствующие позиции из успешного отчёта; не повторять
команду для уже существующей валюты и не заменять её номинал.
Администратор темы для /shopcreate и /stopshop проверяется отдельно.

~~~text

/admscoin -1003376315265:4 "10 золотых монет" 1 = 10
~~~

Количество 1 означает один предмет-связку в реестре, с указанной полной

не создавать. При частично выполненной последовательности снять новый backup

## 3. Проверка всех 15 code после регистрации

Снять новый согласованный SQLite online backup; на его копии:

~~~bash
python tools/inspect_dnd_shop_currencies.py \
  --source /PRIVATE/after-registration.sqlite3 \
  --chat-id=-1003376315265 --thread-id=4 \
  > /PRIVATE/topic4-after.json
~~~

Без --allow-missing успех возможен только при всех 15 корректных позициях.
Проверить complete=true, errors=[], missing=[], 15 различных code/item_id,
основную золотую базу и каждое отношение связки к основной монете.
Проверить неизменность inventory, персонажей и журналов по backup до/после;
посторонние параллельные игровые изменения сверять отдельно, не перезаписывать.

Поле candidate_shop_currency_units содержит полный явный master из всех 15
названий оригинала и реальных code реестра. Это кандидат для человеческого
ревью. Нельзя угадывать или заранее генерировать production code.
После сверки перенести весь candidate_shop_currency_units как
TOPIC_SETTINGS[-1003376315265][4]["shop_currency_units"] отдельным рассмотренным
изменением конфигурации. Значения master должны быть строковыми code, не item_id.

Не переносить целиком TEST app/topics.py в production, не заменять TEST-настройки
production-настройками. Сохранить приватные конфигурации раздельно. Изменение
tracked конфигурации доставляется проверенным коммитом/штатным согласованным
процессом, без локального dirty patch работающего checkout. Этот документ и
инспектор конфигурацию не меняют. Тему 3 не включать даже при наличии её валют.

Для -m явного master достаточно; universal_copper/universal_gold не добавлять
наугад: они принадлежат отдельно подтверждённой шкале -b. Формулы не меняются:
короткий меч 35000 исходных медных → 3.5 золотых, выкуп 0.105 золотых;
-b → 9.975 универсальных золотых при подтверждённой универсальной шкале.

Регистрация валют и master не являются созданием/включением магазина.
До отдельного решения не выполнять /shopcreate. Не создавать buy_enabled=true
и не копировать TEST offers: ассортимент остаётся только ручным, пустым при
отсутствии утверждённых предложений. Перед будущим включением выполнить штатный
preflight каталогов, прав доступа, 15 валют и владельцев.

## 4. Проверка миграции и безопасного возврата приложения

Валидатор на disposable SQLite вычисляет разрешённые добавления
mini_ui_publications из исходного mini_public_shares: исходный operation_key и,
только для share:x:y, совместимый share:x.y. Уже существующие ключи и статусы
не меняются (INSERT OR IGNORE). Каждая иная историческая строка сохраняется
с исходными SQLite-типами. Лишняя/недостающая вставка, UPDATE или DELETE —
ошибка. Игровая миграция Mini не изменяется.

Новые таблицы V1.4.4 сверяются отдельно по явному списку; при первом startup
они пустые, если раньше отсутствовали. После первого startup фиксируется полный
снимок, затем повторные миграции и старый startup обязаны сохранить его целиком,
включая новые столбцы, credit и таблицы обязательств. Инъекции сбоев DDL,
PRAGMA integrity_check и foreign_key_check остаются обязательными.

~~~bash
python tools/validate_dnd_shop_release.py \
  --source /PRIVATE/fresh-production.sqlite3 \
  --source-metadata /PRIVATE/captured-metadata.json \
  --old-ref 5e4d4495a189380542cc643c5c8d723b9351b36b
~~~

--source-metadata используется только для формата с sha256, topics_source и
topics_sha256; исходный metadata другого формата сохраняется отдельно.
Настройки допускаются только как проверенные literal TOPIC_SETTINGS assignments.
Источник не открывается на запись, все init_db/check_bot выполняются на копиях.

Успешный старый startup означает совместимость хранения, не разрешение rollback.
Перед будущим возвратом на рассмотренный SHA 5e4d4495 (версия без обычного /shop)
согласованно закрыть магазины во всех темах, завершить публикации, сверить audit
и выполнить rollback-check --target-ref на копии актуальной мигрированной БД.
Сохранить SQLite целиком, все 16 добавленных таблиц, credit, квитанции, inventory,
SKU/sold и каталог с настройками. Credit остаётся обязательством владельца даже
в приложении без магазина. Старый /shop, игнорирующий enabled, откат блокирует.

Нельзя восстанавливать старую SQLite поверх новых операций или автоматически
разворачивать денежные связки обратно. Возврат приложения/CSV/конфигурации —
отдельное решение владельца с проверкой актуальной копии; защищённые deploy,
backup, lock, PvP-gate и порядок сервисов этим изменением не затронуты.
