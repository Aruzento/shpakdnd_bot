## 2. Зафиксированная пользовательская механика

### 2.1. Маркеры посещённых сцен

У каждого отдельного сеанса истории `(session_id)` один **общий для всех игроков** набор посещённых узлов. Как только узел реально становится текущим для группы, его id считается посещённым. Не посещённые в этом прохождении узлы доступны независимо от того, сколько игроков участвует. Участник не может выбрать личную другую ветку.

Уже посещённый узел никогда повторно не публикуется в качестве новой сцены **в этом сеансе**; ведущая к нему кнопка не отображается. Это касается и любых переходов назад, а не только прямого A→B→A. Старое сообщение уже пройденной сцены может оставаться в Telegram как история сообщений, но его интерактивные кнопки должны стать недоступными.

После завершения/отмены повторный `/story CODE` создаёт **новый** `session_id` с чистыми маркерами.

### 2.2. Предотвращение тупиков — ОБЯЗАТЕЛЬНО

**Недостаточно** отфильтровать только `choice.next in visited`. Это доказанный дефект исходного графа: кратчайший найденный dead-end при наивной фильтрации:

`scene_1 → scene_2 → scene_6 → scene_13 → scene_24 → scene_25 → scene_26 → scene_16 → scene_10 → scene_11 → scene_21 → scene_14`.

В `scene_14` оба варианта направлены в ранее посещённые `scene_25`, `scene_26`. Удаление обеих кнопок оставляет игроков в тупике.

**Правило допустимой кнопки для истории v2:**

1. `next` существует и ещё не присутствует в `visited` текущего session;
2. из `next` существует путь до **любой конечной сцены `end:true`**, не проходящий ни через один узел из `visited` (и без необходимости повторять вершины маршрута);
3. обе проверки вычисляются по неизменяемому `snapshot_json` запущенной истории, на момент отображения **и повторно внутри SQLite-транзакции при голосовании**.

Схематично:

```python
visited = current_session_visited(session_id)
def can_reach_ending(candidate, visited, nodes):
    # DFS/BFS с локальным seen; исключить visited и разрешить законные связи цикла
    # Цель — существование конечного узла без возвращения в уже посещённое.
    ...
visible = [
    (original_index, choice)
    for original_index, choice in enumerate(current_node['choices'])
    if choice['next'] not in visited
    and can_reach_ending(choice['next'], visited, snapshot['nodes'])
]
```

При входе в новую сцену `visited` уже включает эту новую сцену. `can_reach_ending` должен искать в **исходном** графе, не удалять авторские ребра и не использовать необоснованные статические запреты. Для 53 узлов достаточно DFS/BFS с ограничением посещений. Результат должен быть детерминирован по `(snapshot, visited)`.

**Инвариант:** в каждой активной v2-сцене существует хотя бы одна доступная кнопка, пока не достигнута авторская концовка. Если инвариант нарушен из-за порчи состояния — не отправлять «пустую» интерактивную сцену и не завершать историю выдуманным финалом: зафиксировать диагностическую ошибку, сохранить данные, предложить администратору безопасную отмену. Нормальные маршруты обязаны исключить такую ситуацию заранее.

В частности, для `scene_39`↔`scene_40` возвращающие к уже показанной сцене варианты должны отсутствовать, а путь до концовки оставаться возможным.

### 2.3. Учитывать каждый шаг по одному разу

Маркер сохраняется **только при подтверждённом и закоммиченном переходе**, а не при первичном голосе, просмотре кнопок или пробном подсчёте голосов. Действующая сцена отмечается после start. Нельзя повторно выдавать следующий шаг при replay старого callback, restart, конкурентных голосах или admin kick.

## 3. Контракт JSON и совместимость

Предлагается **аддитивная схема** `schema_version: 2` с полем `visit_policy: "once"`.

- `schema_version:1` — старый неизменный DAG-контракт: **циклы по-прежнему запрещены**, без новой фильтрации, старые сессии/снимки работают как прежде.
- `schema_version:2` + `visit_policy:"once"` — допустимы направленные циклические ребра, но runtime гарантирует запрет повторного посещения и проверку пути к финалу. Все остальные проверенные поля, ограничения и безопасность v1 остаются; лишние поля не разрешать.
- Исходные ids `scene_1`..`scene_46` и `ending_k1`..`ending_k7` — стабильные маркеры. Не заменять `next` на название сцены, не переименовывать id без миграционного плана для frozen snapshots.
- Проверять уникальность code между внешними JSON, типы, корректность ссылок, начальный узел, достижимость всех узлов из старта, наличие семи достижимых концовок; каждый исходный не-конечный узел должен иметь путь к какой-то концовке в графе (до учёта маркеров). Схема без конечных узлов недопустима.
- Не допускать `next` на несуществующий id, циклическую ловушку без выхода к `end`, нарушение ограничения 1000 nodes, 20 choices, UTF-16, файлового размера 2MB. `story.catalog.discover()` продолжает изолировать повреждённый файл, не ломая здоровые истории.
- HTML/скрипты/произвольные поля в JSON не исполнять. **Никаких** `award`, `loot`, `money`, `items`, встроенных условий или вызовов механик D&D / Mini.
- Не подменять JSON v2 JSON v1 и не убирать авторские варианты ради прохождения старого валидатора: задача именно в защите реальных динамических маршрутов.

## 4. SQLite, сохранение состояния и миграции

Использовать текущий `story_steps(session_id, step, node_id, choice_id, next_node, result_json)` и `story_sessions(id, node_id, snapshot_json, step, status...)` как **источник уже зафиксированного пути**:

- `visited_nodes = {current node_id} ∪ {node_id, next_node для всех committed story_steps конкретного session_id}`;
- у нового start `visited={start_node}`;
- вычислять/возвращать `visited_nodes` для runtime/status/render из DB в том же согласованном контексте и снапшоте; не смешивать маркеры разных session_id, чатов или тем;
- не вводить новую колонку, если описанного журнала достаточно. При неизбежной миграции сначала доказать необходимость, сделать аддитивной и идемпотентной, проверить на старых копиях и предоставить rollback/backward-compatibility сценарий;
- не пересчитывать уже сыгранную историю при hot-edit JSON: `snapshot_json` зафиксирован в `start()`;
- транзакционность через имеющийся `BEGIN IMMEDIATE`, защита operation_key, прежние `story_votes` и `story_publications` без дубликатов;
- читать только замороженный набор `nodes` в активном сеансе, не live файл.

**Особое внимание:** старый код при rollback может не знать v2 и не уметь продолжать начатые v2-сеансы. До разрешения production нужен конкретный порядок остановки/запрета новых v2-сессий и завершения/безопасного сохранения активных, чтобы возвращение старого кода не портило состояние. Нельзя объявлять совместимый rollback только потому, что схема SQLite не изменена.

## 7. Тестирование и совместимость (ОБЯЗАТЕЛЬНО)

### Unit

- V1 запрещает любые циклы, сохраняет прежний результат; v2 принимает данный граф 53 nodes/113 choices/7 endings.
- Дубликаты ids, неверные `next`, неизвестные поля, неправильный `schema_version`/`visit_policy`, недостижимые сцены/концовки, недопустимые размеры/тексты, ловушки без финала отклоняются.

- Фильтр скрывает прямой возврат и не даёт обойти запрет через длинную цепочку. Например, `scene_39 ↔ scene_40`.

- Подсчёт вероятности равного количества голосов, выбор tie один раз, восстановление процента и кнопок.
